# Text tools for reading the Lean source

These are text tools; they find where to read, they do not prove a dependency. Python 3, standard library
only. Each one runs its own self-test first and refuses (exit 4) if it fails. `--selftest` shows the cases. In `notes_meta.py` a case id registered twice stops the tool at load with a message naming the id and both descriptions; ids are compared as exact strings, so `rec1`, `REC1` and `REC1 ` are three ids.

A run that checks nothing (no `.lean` file under SRC_ROOT) writes nothing. If OUT_DIR already holds a file that run
would have written, an earlier result looks like this run's to the next tool; so `scan_graph.py`, `alias_edges.py`
and `decl_table.py` print one more line after `CHECKED NOTHING`, `OUT_DIR holds files from an earlier run: <names>;
this run wrote nothing`, and keep exit 1. They do not delete the files.

For whoever writes the next self-test: **the expected value in a case is a literal, never read back from the tool.**
A case that computes its expectation with the code under test, or with a helper the tool exports, passes whatever
the tool does. Write the number, the line or the list into the case, and run a wrong version of the tool (a copy)
to see the case go red.

**`tools/scan_graph.py SRC_ROOT OUT_DIR`** answers: which files exist, how big, what do they import?
It writes `files.tsv` (one row per file, with word counts) and `edges.tsv` (one row per internal import).
`python3 tools/scan_graph.py SRC_ROOT OUT_DIR`

**`tools/alias_edges.py SRC_ROOT OUT_DIR`** answers: which theorems are only a wrapper around another
theorem, where is the target declared, and where are the names written out in full? It never picks
between two declarations with the same full name; it lists both.
`python3 tools/alias_edges.py SRC_ROOT OUT_DIR`

**`tools/decl_table.py SRC_ROOT OUT_DIR`** answers: which named declarations are in each file, on which lines?
It writes `decls.tsv` (module, name, kind, first line, last line, basis) and `decls_dup.tsv` (every row whose
module and full name occur more than once; it never picks one). The lines are the text rule's extent, not Lean's;
the rule lives in `tools/lean_decls.py`, which `alias_edges.py` also uses. `example` lines and instances with no
name are not rows; they are counted on the second summary line.
`python3 tools/decl_table.py SRC_ROOT OUT_DIR`

**`tools/rh_anchor.py`** is a small library, not a command: the one place that knows the anchor format of the
notes. A note carries its metadata in one-line comments, `<!-- rh-note {...} -->` (the header) and
`<!-- rh-block {...} -->` (a block anchor, on its own line after the paragraph, table or lean block it anchors),
so the rendered page does not change. The checker and the helper that writes anchors both import it. It reads and
writes the lines (`parse_note`, `format_comment`, `strip_anchor_lines`), says which element an anchor follows and
where a new one goes (`target`, `target_at`, `insert_after_line`; a new anchor goes at `append_after`, after any anchors already there), checks the shape of a block or header
(`problems`, `header_problems`, `block_id_ok`), reads the run of elements a `sketch` block covers (`run_at`) and numbers new ids (`next_block_id`). It checks shape only: not the
outline, not the declaration table, not whether a table row exists. Markdown is approximated by three rules (fences,
tables, one comment per line), not CommonMark; the LIMIT paragraph in the file lists what is not recognised.
`python3 tools/rh_anchor.py --selftest`

**`tools/notes_meta.py NOTES_DIR OUTLINE DECLS_TSV`** answers: is the metadata of the notes well formed, and does every
name in it resolve to one row of `decls.tsv`? It reads the outline (every group, its parent, level, order,
premises, roots and claim), each note's header and anchors, and, with options, more: `--src SRC_ROOT` checks that
a block's `file` is in the note's file table and its `lines` are inside the file, `--strings PATH` lists blocks
whose text opens with another kind's frame, `--base REV` checks that the note at REV and the current note, both with
their anchor lines removed, are equal byte for byte after that rule, except that text the note only GAINED as dated additions is listed, not refused (see below; this needs the `git` program; `--repo DIR` names the repository when it is not the one around
NOTES_DIR), `--today YYYY-MM-DD` sets the day the additions are checked against (a test hook; default the UTC date of the clock), `--glob PATTERN` changes which files are notes (default `[0-9][0-9]-*.md`, so this folder's
`tools.md` is not one). The format of the comments is read only through `rh_anchor.py`. A finding is one line,
`CODE path:line message`; `EXTENT-WARNING`, `FRAME-NOTE`, `NEW-NOTE`, `ADDITION`, `CLAIM-LIBRARY-WORD`, `ROOT-ROLE-MISSING` (while it is not required) and `RECOGNITION-WORD` are listings and never fail the run. Each
note prints `note <id> header ok, blocks N (kind=count ...)`, and the run ends with the counts by kind, what the
in-file and byte checks did or did not do, and `N notes, M findings, K warnings`. It checks shape and resolution;
it does not judge whether a claim is right, and the LIMIT paragraph in the file lists the title rules and the
translation rules that need a reader. Every group needs at least one root; a group with a null claim and no root passed
in the first version and is now a ROOT-COUNT error. The title rules the script applies are heuristics, named in the LIMIT. A dotted token (`Foo.bar`) or a CamelCase word (`getValue`) in a claim `text` or a `conditions` entry outside single backticks is listed as `CLAIM-LIBRARY-WORD` (once per token and text; a prompt to write it in backticks or in plain words, not a proof; the rule is exact in the LIMIT). A claim may carry `basis` (`read` or `census`), optional for now; a summary line counts the non-null claims that are objects by basis (a claim that is not an object is its own BAD-VALUE and is counted in none). A group may also carry three optional keys. `root_role` (`result`, `named_statement` or `object`) belongs to a claim, and the checker compares it with the kind of the group's root in `decls.tsv`: `result` if and only if the kind is `theorem` or `lemma`; every other kind (`def`, `structure`, `abbrev`, `inductive`, any other) takes `named_statement` or `object`; a mismatch is `ROOT-ROLE`. A claim with no `root_role` is a `ROOT-ROLE-MISSING` listing for now (the real outline has no roles yet) and an error once the constant `REQUIRE_ROOT_ROLE` is set to True. `recognition` says where we read the statement stands: a `form` (`known`, `variant`, `not_recognised`, `open_in_literature`), `reader` and `date`, and per form a `result` in plain words, `citations` (each with `source`, `where`, `opened_by`, `opened_on`, and optionally `url`, `source_date`, `says_open`) and a `difference`. The form `not_recognised` may also carry one optional `note`, a string that is not blank, saying what the step is in the release's own terms and what we looked for; on any other form with a known form `note` is `RECOGNITION-FORBIDDEN`, and `result`, `citations` and `difference` stay forbidden on `not_recognised`. The number of sentences in a note is not checked. It is refused on a null claim; `open_in_literature` is only for a `result` or a `named_statement` (on an `object`, or with no `root_role`, it is `OPEN-ROLE`; `established` stays for a named statement only), needs a citation with `says_open` true and its `source_date` (a year `YYYY`, a month `YYYY-MM` or a day `YYYY-MM-DD`, each a real date, validated here, and the page builder will print it as written; year 0 is refused; `opened_on` stays a full `YYYY-MM-DD`); the words `novel` and `unprecedented` in `result`, `difference` or `note` are an error, and `new`, `original`, `first`, `assume`, `assumes`, `assumed` are listed as `RECOGNITION-WORD` (a prompt to the signer and the reviewer, not a proof; a word inside single backticks is checked too). A named statement may carry `established`: `not_traced`, or the theorem or lemma (`by`, which must resolve to one row of that kind) with its reader and date; that its conclusion is the named statement is the reader's claim. The run prints `recognition: K known, V variant, N not recognised, O open in literature, M not written, of G groups with a claim` after the `claim basis:` line, counted by the tool and asserted to add up (`SUM-RECOGNITION`). The check of these fields against the lines of the release is the builder's, not this tool's. The third key, `title`, is a plain string written by the author: a noun phrase that names the role of the step (the term a definition defines, or what a step with no claim is), never a sentence. It is not empty, has no blank at either end and no line break (anything else, an object or a list included, is `BAD-VALUE`), and its first character is not a lowercase letter (`BAD-VALUE`, `title must start with a capital letter or a character that is not a lowercase letter`: a digit, a quote, a bracket, a symbol or a letter with no case passes, a Greek or accented lowercase initial is refused, and the author writes the capital since no code changes author text; a title with a shape fault has that finding alone, and the build stops on the checker's errors); it carries no reader, date, conditions or recognition. The page shows it on a card with no claim and on a definition or structure card, so a title on a group with a claim that is not a definition card by the shared predicate below (the group's `root_role` when it has one, else the kinds of its roots in `decls.tsv`; a root with no row is not judged; a group with a claim has one root, so several roots are `ROOT-COUNT` as well) is `TITLE-WITH-CLAIM`: an error, because a title the page would ignore is author text no reader sees, and the author must choose. A bad title is `BAD-VALUE` alone. A `sketch` block (a reader's short account of a proof, written after the idea) carries `reader`, `date`, `decls`, `basis` (`source` or `compiled`; `compiled` needs a `build` string and `source` refuses one), and optionally `unexpanded` (a list of strings: what is left, printed on the reader's surface), `unexpanded_detail` (F53: a list of non-empty strings, the per-file entries with tactic names and line numbers, printed inside Evidence only; the list may be empty, absent is the same as empty, and only a sketch reads the key) and `span` (an integer of 1 or more, default 1: how many elements, ending at the one the anchor follows, the sketch covers). Only a sketch may carry `span`, and a sketch carries no `item`. The run may hold paragraphs and lists; a table, a fence, a heading, a quote, an HTML line or another anchor inside it is refused, and so is a span larger than the elements between the anchor and the previous anchor, heading or the start of the note. A block belongs to the group named in its note's header and anchors a root of that group when its `decls` include the root; the counts run over all the notes of the group. The checker refuses a sketch whose root has no argument block (`SKETCH-NO-ARGUMENT`), a second sketch on one root (`SKETCH-DUPLICATE`, naming both block ids), a sketch on a root that is not a result (`SKETCH-ROLE`: the group's `root_role` when it has one, else the kind in `decls.tsv`, theorem or lemma; each root of a null-claim group by its own kind), a sketch whose `decls` hold no root of its group (`SKETCH-ROOT`), and a span the run cannot cover (`SKETCH-RUN`, with the reason from `rh_anchor.run_at`). An argument block anchored on a root whose kind is not theorem or lemma is listed as `ARGUMENT-NO-PROOF`: a prompt to the reader, since a definition can carry small proofs inside; it never changes the exit code. The note line and `blocks by kind:` count seven kinds. The line `sketches: S of P steps with a proof read` is not printed by this tool: what a step is belongs to the builder, which counts it. `note_cite.py` is unchanged: its `--kind` takes the kinds from `rh_anchor`, but it has no flag for `basis`, so a sketch cannot be valid through it and is refused as `BAD-BLOCK`. Two notes whose headers carry the same `id` (exact strings, first header of each note) are `NOTE-ID-DUPLICATE`. **Dated additions.** A note may gain text after publication without a byte difference when every base line is still there, unchanged and in order, and each run of new lines begins, after any blank lines, with a heading (one to six `#`, a space, text) whose text holds a real date `YYYY-MM-DD`. The base is matched into the current text from the left (a repeated line is taken at its first match) and, if that leaves an illegal run, from the right (taken at its last match); the note is accepted when either gives only legal runs, and the runs of the first that does (left first) are listed. Two alignments are tried, not every possible one. Every real date in the heading may not be later than the day of the run and may not be earlier than the date in `release` of the note header **as published** (the text at `--base`, so editing or deleting `release` since then does not lower the limit) when that is written `rh-YYYY-MM-DD`; a published release with no date, or an impossible one such as `rh-2026-02-30`, gives no earlier limit, and the limit is the release's date, not the note's own. A run may not touch published text: the line before its first non-blank line and the line after its last one must each be blank or the edge of the note (a blank line inside the run counts; anchor lines are not text), otherwise it is a byte difference naming the run and the side; a run above the first published non-blank line (above the title) is one too. Fence state is kept: a published line that is inside a fenced block in one text and not in the other (an inserted marker that wraps published text in a code block, or ends a published block early) makes the note a byte difference, and the message names the inserted run. Each such run is printed as `ADDITION path:LINE N lines, heading TEXT` (the line in the file as it is on disk, N the lines of the run), is counted among the warnings, and never changes the exit code; the byte-check line ends `additions A`. Everything else stays a byte difference: a removed or altered base line, a run with no dated heading first, a date outside the window (the message names the date and the window), an impossible date such as `2026-13-45`, and a run inside a fenced block of the published text. One run that fails makes the whole note a byte difference. Two limits: a line that repeats an earlier base line can leave the original unmatched as a second run on both alignments, which then fails unless it is itself a dated addition; and a note whose last line has no line ending cannot gain text after it. The boundary rule looks at blank lines only, so a run that brings its own blank line on each side and sits between two table rows, or inside a list item, is accepted and splits that table or list. A byte difference is reported at its line in the current file as it is on disk (and its index without anchors), so a reader opens the file at that line; where text is missing from the current file the number points past the end of the text: the line after the last non-anchor line, which is an anchor line when anchors trail it and otherwise one past the last line of the file (not a line that exists), or 1 when the file has no non-anchor line. The strip rule is `rh_anchor`'s: a last anchor line with
no line ending of its own also removes the line ending before it, so adding or removing such a hand-typed last line can read as a
one-line-ending difference; anchors written by the helper carry their own ending. An anchor-looking line counts as text only inside
a fence, and a malformed `rh-` line is kept as text, so fixing it since REV is a byte difference. A block anchored to a list must name its top-level
item (`item`, 1-based, counted across blank lines: a loose list is one list; nested items are not numbered), except a `sketch`, which covers whole elements, a list included as a whole: a sketch whose target is a list is not asked for `item`, and `item` on a sketch is a block problem (`BLOCK-PROBLEM`, with none of the other item findings beside it); shapes of list a renderer may show differently are refused through a table
that is empty until the renderer control is in, for the anchored list of any block and, for a sketch, for every list in its run (a list that is not the target is named with its first line; a sketch with a bad span or an illegal run gets that finding and no shape finding). Limit: the shape keys `last_nested` and `followed_by_paragraph` describe an anchor adjoining a list, and no anchor follows a list in the middle of a run, yet the table is applied to every list as written, so whoever fills the table decides whether those two keys apply to a list that is not the target. The run prints a count line for the outline (and for the strings file and the
byte check when they ran); a header's group may be `root` only at level 0.
`python3 tools/notes_meta.py NOTES_DIR outline.json decls.tsv [--src SRC_ROOT] [--strings strings.json] [--base REV] [--today YYYY-MM-DD]`

**Editions (F44).** A published text is rewritten in place only in a change that raises a group's `edition` from 1 to 2 and gives it an
`edition_date`; `notes_meta.py` with `--base REV` reads `outline.json` as it was at REV and compares each group's reader-facing text
(the fields in `EDITION_TEXT_FIELDS`: the claim text and conditions, the recognition's result, difference and note, each citation's
`where`, `source` and `source_date`, `established`, and the group's `title`, which is reader-facing text and is compared as text). Every field whose own text the page prints outside its Evidence section is in that list. The fields that only choose which sentence the page prints (`recognition.form`, `root_role`, `claim.basis`, a citation's `says_open`) and `premises` (what a step rests on) are not text: a change to one is a change of substance, not a rewrite for readers, so the check lists it, with or without a bump, as `SELECTOR-CHANGED <id> <path> <old> -> <new>` (exit code unchanged; the summary says `selector changes: K`) and never compares it as text. The compare is strict on purpose: text byte for byte (a space, a newline, NFC against NFD is a change), lists in order (a reorder or a duplicate is a change); an empty list and no value are equal. A change with the bump prints one `EDITION` line (none beside a bad `edition_date`) and does not fail the run; a change
with no bump, a bump with no change, a second rewrite, an edition 3, a lowered edition and edition 2 on a new group are errors; a group
that left the outline is a `GROUP-GONE` listing; an outline that cannot be read at REV (missing, not JSON, no groups list, or a groups list holding a non-object) is one `OUTLINE-BASE` listing and the rule does not run; `groups: []` at REV is legal and compares nothing.
`build_site.py` writes `edition` into each group file and into `data.js` (`null` at edition 1, else `{"number": 2, "date": "..."}`), counts
the groups at edition 2 in `manifest.json`, says it once on the first screen (the latest date, and a link to the tree of the first edition)
and once in each rewritten card's Evidence section (that card's date, and a link to `outline/outline.json` of the first edition). The
wording and the two addresses are the strings keys `edition_note_first_screen`, `edition_note_card` (the sentence of a group at edition 2),
`edition_note_card_note` (the sentence of a note, see below), `edition_link_label`, `edition_href_tree` and `edition_href_blob`; the addresses must be https and are not sentences. The static check lets an `<a class="edition-link">` with an
https `href` through, by class token, as it does a citation anchor. A page with no group at edition 2 is byte-equal to a page built before.

**Links to the notes (F60).** The website does not serve the notes' markdown files, so a relative note link (`notes/<file>`) answers 404 there. The
strings key `note_href` therefore takes a second, optional placeholder `{commit}` (the first is `{file}`, the note's file name, percent-encoded), and
`site/strings.json` holds `https://github.com/engram-agents/riemann-explained/blob/{commit}/docs/{file}`. `{commit}` is filled with the FULL notes
commit of the build (40 lower-case hex digits, the `commits.notes` that every JSON file carries), never with a branch name: a card's record of what
was read is a record at that commit, and a link that follows `main` could show text the cards have not been checked against. The address is the
`link` of every note in the group files, `level0.json`, `level1.json` and `data.js`, and the `href` of every note anchor on the page. A template that holds
`{commit}` when the build has no full notes commit (no `--notes-commit`, a tree with uncommitted changes, which stamps `dirty`, or any id that is not
40 lower-case hex) is refused: `BUILD-ERROR NOTE-HREF-COMMIT note_href holds {commit}, but the build has no full notes commit (it is <id>; give
--notes-commit and --repo, and build from a clean tree)`, exit 1, nothing written. A build from an unclean tree is refused because the stamped notes id is `dirty`, so to preview uncommitted notes, build with a copy of the strings file whose `note_href` is the relative `notes/{file}`. A template without `{commit}` builds exactly as before whatever the
commit is (both placeholders are optional). The static check lets an `<a class="note-link">` with an `https://` `href` through, by class token, as it does a
citation or an edition anchor; it is the one new exemption, and nothing else changed (`note-link` with `http://` or `//`, as part of another class word, on an
`img`, a form, a `<link>`, or on `src`, `action`, `formaction` or `xlink:href` is still refused, and so is an https note anchor with no `note-link`). The
builder writes the class on a note anchor if and only if its link starts `https://`, at the five places the page shows one (the notes about the whole in
the header, the argument's read-more link, the corrections list, a card's notes list and the block line of the Evidence section), through one helper,
`_note_open`; a relative template gives anchors with no class. The placing step is unchanged: the notes are not copied to the site.

**Editions of a note (F44B).** A note's header may carry `edition` (the integer 1 or 2; absent is 1) and `edition_date` (a real date
`YYYY-MM-DD`, not later than the day of the run; required at edition 2, refused at edition 1 or absent). `rh_anchor.header_problems` checks the
shape and `notes_meta.py` reports each bad value as a `BAD-VALUE` on the header line (edition 3 or more says `edition 3 needs a ruling`).
With `--base REV`, `notes_meta.py` compares the note without its anchor lines against the note at REV (a base with no header, or no
`edition`, is edition 1; so is a base whose header cannot be used for any reason other than an unusable `edition` value, which is the
`EDITION-BASE` listing below). A note is found at REV by its file name; a note renamed since REV is paired with its old name by its header `id` (see F52 below). A bump to edition 2 on a note whose text changed is one `EDITION` listing, `EDITION <note> +A -R lines, edition 1
to 2, <date>`, where A and R are the lines added and removed by `difflib.SequenceMatcher` over the lines (a replaced run counts on both
sides, a moved run counts on both); the note then has no `BYTE-DIFF` and no `ADDITION`. A bump with the text unchanged is `EDITION-EMPTY`
(an error). A note at edition 2 at REV follows the ordinary rules (a dated addition is legal, any other change is `BYTE-DIFF`); edition 1 or
none after edition 2 is `EDITION-DOWN`, a changed `edition_date` is `EDITION-DATE-CHANGED`, and edition 2 on a note that is not at REV is
`EDITION-NEW-NOTE` (errors). A base whose edition is not usable is an `EDITION-BASE` listing and the rule does not run for that note. For a
note at edition 2, `EDITION-BLOCK <note> <block id> element <n> <kind> -> <n> <kind>` lists each block (matched by id) whose target element
changed its place in the note (the n-th element, headings counted) or its kind, and `EDITION-BLOCK <note> <block id> gone` a block that is
no longer there; these are listings and say nothing about wording. The run prints `edition check: N groups compared to REV; K notes compared
to REV` and `editions: K of N notes and J of M groups at edition 2`. A bump whose `edition_date` is missing, not a real date or later than
the day of the run keeps its `BAD-VALUE` (an error) and the rule still prints its own line, `EDITION <note> +A -R lines, edition 1 to 2, no usable
date`, or `EDITION-EMPTY` when nothing changed, so the text change is not hidden behind the bad date.

**What no bump covers in a note (F52).** With `--base REV`, `notes_meta.py` also compares the parts of a note that are not its text.
A note's `list_title` is author text (the heading of its link on the page) and is compared like a group's title: a change with no bump is
`BYTE-DIFF <note> list_title changed from <old> to <new>` (an error; also at edition 2 at REV), and under a bump it counts as one removed and
one added line of the `EDITION` listing, so a bump whose only change is the title is not `EDITION-EMPTY`. A note's `group` and `level`
say where it is shown: a change against REV is the listing `PLACEMENT-CHANGED <note> <field> <old> -> <new>` (one per field, `group` first, at
any edition, exit code unchanged). An anchor that now points at a different element than at REV is the listing `RE-POINTED <note> <block id>
<old first words> -> <new first words>` (blocks matched by id; the element differs when its kind differs or its first 8 words differ, not when only
its ordinal moved, so a dated addition above it is not a re-pointing; when the first words are equal and only the kind differs, for example a table and a paragraph line that reads the same, the line ends with the two kinds, `(table -> paragraph)`; a note at edition 2 gets `EDITION-BLOCK` instead, not both). Re-pointing
an anchor is a repair, not an edition: a bump whose only change is where anchors point is still `EDITION-EMPTY`. A note at REV that is not in
the tree now is the listing `NOTE-GONE <note>`; if exactly one note is gone and exactly one new note has the same header `id`, it is
`NOTE-RENAMED <old> -> <new>` instead, and the new note is checked against the text of the old name (a rename with a rewrite and no bump is
a `BYTE-DIFF`; a rename with a bump is an `EDITION` listing; no `NEW-NOTE`). Two notes with one id on either side is no pairing. The four
listings are read by the gate and never change the exit code. The summary prints `placement changes: K`, `re-pointed blocks: K`, `notes gone: K`
and `notes renamed: K` (each `did not run, no --base given` without `--base`).
`build_site.py` writes `editions` into each group file and into `data.js`: a list of `{"note": "<file>", "edition": 2, "date": "..."}` for the
notes of that card at edition 2, in note order, `[]` when none (the notes of a card, for this list and for the paragraphs below, are the notes whose
header `group` is the card and the notes of which the card shows at least one block, whichever group the note's header names; a note is listed once,
however many of its blocks the card shows and whether or not it is also the card's header-group note, and a level-0 note is never listed); `manifest.json` keeps `editions` as the number of groups at
edition 2 and adds `note_editions`, the number of notes at edition 2. The first-screen sentence appears when a group or a note is at edition 2,
with the latest date over both. A card's Evidence section gets, after the group's own paragraph (the group's sentence is `edition_note_card`,
which says the text of the card was rewritten), one `edition_note_card_note` paragraph (the note's sentence: it says a note the card
draws on was rewritten, because a card prints only the blocks of a note and the edition check compares the whole note file)
for each edition-2 note of the card (header group or shown block, as above: a card that shows a block of another group's edition-2 note prints that note's paragraph, linking the note's own file), whatever the dates (a note dated the same day as the group's edition gets its paragraph too: the group's paragraph links the outline file and the note's links the note's own file, two sentences and two files, so the second is not a repetition of the first), each with the
note's date and a link made from `edition_href_blob` with `{file}` = `docs/<note file>` (the file name percent-encoded as the note's own
link is). A level-0 note (a note about the whole proof) gets no card paragraph, even when its header names a real card as its group: it is
not in that card's `editions`, but it is counted in `note_editions` and its date counts for the first screen. The page (`index.html`) of a
build with no group and no note at edition 2 anywhere is byte-equal to a page built before; the data files (each group file, `data.js`,
`manifest.json`) still gain `editions` (`[]`) and `note_editions` (`0`). The checker refuses a bad edition first; if one reaches the builder
(F52) it refuses with a message and writes nothing, never a traceback: a group or note at edition 2 whose `edition_date` is missing or not a
string is `BUILD-ERROR EDITION-DATE <id> edition 2 needs an edition_date`, and an `edition` that is not the integer 1 or 2 (a boolean and 2.0
included) is `BUILD-ERROR EDITION-VALUE <id> edition must be 1 or 2`; every bad group (outline order), then note (file order), is listed.

**`tools/note_cite.py NOTE DECLS_TSV --at LINE --decl FULL.NAME --kind KIND`** writes one block anchor, so nobody

The built page is also checked against one list of the elements it may hold, and the attributes of each (`ALLOWED_ELEMENTS` in `build_site.py`: 40 elements and 55 element-attribute pairs); no other element or attribute name may be on it. The check reads the start tags of the built `index.html` after it is rendered and before anything is written (not the CSS, not `data.js`), and looks at element names and attribute names only: attribute values and the text inside `<style>` are not checked here, and a `javascript:` or `data:` value of an `href` is a limit of the separate static check, which looks only for http(s) and protocol-relative addresses and the request APIs. The list is the 28 elements and 17 pairs the builder emits, measured over the five self-test fixture pages (EL4 pins them; an entry no path emits is not kept: `<time>` was removed when the dates left the page), and the MathML set, which the formula converter writes (a page with a formula holds it; the fixture pages do not). That set is 12 elements (`math mrow mi mn mo msub msup msubsup mover munder munderover mspace`), with `mathvariant`, `stretchy` and `form` on those only, `width` on `mspace` alone and `accent` on `mover` alone. The 17 pairs of the page are `class` on `a article details div dl h3 li p section span ul`, `href` on `a`, `id` on `article`, `lang` on `html` and `charset`, `content` and `name` on `meta`; which `meta` tags may stand is a separate rule, below (F55). An element or an attribute outside the list (a `<script>`, an `<annotation>`, an `<iframe>`, an `onclick` on a `<p>`, an `href` on a MathML element, a `style` where the builder has none) is refused as `PAGE-STATIC element <name>` or `PAGE-STATIC attribute <name> on <element>`, exit 1, nothing written, the same code as the other static findings; every bad attribute of a tag is listed, each against its own element's list (a `data-*` attribute is refused too). `style` and `title` are the allowed elements `html.parser` reads as text wherever they stand (the check takes this set from the parser's own lists, and a case pins it, so a future raw-text element must be classified); a browser reads their content as text only in HTML content, and as markup directly inside MathML, where the parser would not report a tag behind them. So each is allowed only in the opening run of the page, the start tags before the first one that is not `html`, `head`, `meta` or one of them (on the real page: `html`, `head`, `meta`, `title`, `style`), and refused after it, as `PAGE-STATIC element <name> outside head` (measured with html5lib 1.1: `<math><style><img src=x onerror=alert(1)></style></math>` builds an `<img onerror>` there, and the name check alone returned nothing). The rule reads start tags, because an end tag that a browser ignores (`</head>` while `<math>` is open, `</body>`) pops what `html.parser` tracks and not what a browser tracks: a rule built on end tags was passed by `<head><math></head><style>` and `<body><math></body><style>` (and the same with `title`), each a live `<img onerror>` in html5lib 1.1. No end tag reopens the run; the one end tag looked at is `</head>`, which only closes it, so it can add a refusal and never remove one. **What this does not claim:** the check is a name check on the tags as `html.parser` sees them, not a browser-grade parse, and a page it passes is not shown to parse to the same tree in a browser. Other differentials between `html.parser` and the HTML spec's parser are known to exist and are not measured here: the MathML text integration points and `annotation-xml`, attribute quoting, and how a misnested tag ends (the other raw-text elements are not allowed, so they are refused by name). Comments and CDATA are no longer on that list, because they are refused by construction: every comment (an ordinary one too, and `<!x>`, which the parser hands over as one) is `PAGE-STATIC comment`, every processing instruction is `processing instruction`, and every declaration but one `<!doctype html>` before the first start tag (compared lower-cased, so the page's `<!DOCTYPE html>` is the same doctype) and every unknown declaration such as `<![CDATA[` is `declaration`; markup `html.parser` still holds back at the end of the page (an unterminated comment, CDATA section, tag or style, which it never reports and a browser still reads) is `unterminated markup`. That is stricter than a browser needs: a comment is harmless to a browser, and the page has none (measured: no comment, no processing instruction and one declaration, `<!DOCTYPE html>`, on the real build and on every fixture page the self-test builds). Only the opening run may hold a raw-text element: a page that needs one elsewhere must change this rule, with its case. The search that found no page passed by the rule with a live `<img>` was bounded (html5lib standing in for a browser, a hand-picked pool of the allowed start tags and five end tags, one to three tokens before the payload; a second search put comment, CDATA, processing-instruction and doctype tokens in front of an `<img onerror>` after the real `<body>`) and is not part of this repository. A new element or attribute on the page is a change to this list in the same change, with its case.

**The head of the page (F55).** After `<meta charset="utf-8">` and before `<title>` the head holds exactly two more lines, byte for byte, each once: `<meta name="viewport" content="width=device-width, initial-scale=1">` and `<meta name="robots" content="noindex">`. The first is for phones: without it a phone lays the page out at 980 px and scales it down to about 40 percent. The second is the builder's own instruction not to index the site: the site is served byte for byte, so no server adds one, and the instruction has to be in the page. Every other byte of the page is as before (four fixture pages, with the two lines removed, have the digests they had; the digests `ED4` and `UD12` pin moved by exactly these two lines). The element check above keeps `charset`, `content` and `name` as the attribute names a `meta` may carry, and a separate rule says which whole tags may stand: the charset tag and these two, each a literal tag (attribute, value and order), not "any name and content". Any other `meta` is refused as `PAGE-STATIC meta not listed` (an `http-equiv`, a `charset` of another value, a bare `meta`, the right attributes in another order), `meta name not listed` (a name that is neither `viewport` nor `robots`, `Viewport` too), `meta viewport content differs` or `meta robots content differs`; one of the three tags twice is `meta repeated`. Cases `HD1` to `HD5`.

**The build checks the head itself (F55, round 1).** `head_meta_problems(page)` reads the rendered page text, and `run()` calls it beside the element check (it is not part of `element_problems`, whose cases feed pages with only a charset tag). So a builder that drops a tag no longer ships a page without it; before this check only the fixture cases noticed. The check looks for the two literal tags, fixed when the file loads, so a change of the builder's own constants does not change what it looks for. Cases `HM1` to `HM3`. In the browser helper, an unsolicited WebSocket pong is ignored (`HD7`), and a page that never reports `readyState` `complete` fails as `the page did not finish loading in N polls of 0.1 s` (`HD8`, which drives the helper with a small stand-in for the browser written with the standard library, so it needs no Chromium).

**The title of a card (F47, F48).** A group may carry a `title` (see the checker above); the group file and `data.js` carry it as written, `null` when there is none, and the level files carry none. A *definition card* is decided by THE definition card predicate (`definition_card` in `notes_meta.py`, which `build_site.py` loads and calls, so the checker and the builder share it): a usable `root_role` decides (`named_statement` and `object` are definition cards, `result` is not; a null claim has no role); with no role, a card is a definition card when it has a root and NO root, of any number, is a theorem or lemma; one theorem or lemma root among several makes it a result card; an unknown or empty kind is not a result kind, so it is a definition card; no root is not a definition card. A card needs a title (`needs_title`) when it has no claim or is a definition card. Any other card is a *result card*. The heading of a card, in the same `<h3>` as before: (a) no claim, a title, a result card: the label `title_label` (`What this step is:`) in `<span class="title-label">`, then the title in `<span class="title-text">`, then directly under the heading `<p class="no-claim-label">` with the `no_claim_label`, then the premises line (if any) and the status lines as before; the root's Lean name is no longer in the heading and stays in Evidence. (b) no claim, a title, a definition card: the same, with `definition_label` (`Definition.`) in `<span class="definition-label">` instead, and no joining word. (c) a claim and a title, a definition card: the heading is `definition_label` and the title only; the statement is the first paragraph under the heading, `<p class="definition-statement">`: the title, `definition_join` (`is defined as:`) and the claim text as a claim is rendered (formulas converted inside it, logged under the card id), in normal weight; the conditions list follows that paragraph. A definition card with no claim prints no join anywhere. (d) a claim and no title, or no claim and no title: as before. A result card with a claim is shown by its claim whatever the data holds. The title goes through the span rule and the formula rule like every author-written line, and is escaped like every string. The title text is in normal weight, no colour, one CSS rule (`.title-text`): the heading is bold, so the weight is what sets the title apart from the label. A premise row and the shared-root note (the two places the page names another card, `title_of`) show the title of a card that has a shown title, else the claim, else the root name. The shared-root note (`shared_note`, placeholder `{groups}`) names each other card that shares the root, as an in-page link to its card, joined by `, ` in the order of the ids; the group file keeps the ids as data (`shared_with`). No card's id is printed as text: it is in the `id` attributes and the `#` links only. A card that needs a title (no claim, or a definition card) and has none is listed `TITLE-MISSING <card id>` on standard output, in the order of the page, and the line `titles: T of K cards that need one` follows the facts check; while the constant `TITLE_MISSING_REFUSES` is False this never changes the exit code, and set to True the same cards refuse the build (`BUILD-ERROR TITLE-MISSING <card id>`, exit 1). `TITLE_MISSING_REFUSES` is False until the outline carries every title.

**Formulas (F26B).** A formula `$...$` on one line, outside code spans and link targets, is shown as inline MathML in every place the page shows author text: a claim, a condition, a note's list title, the first sentence and the text of an argument or interpretation block, a sketch's paragraphs, items, sub-items, `unexpanded` entries and `unexpanded_detail` entries, the recognition's result, difference and note, and a citation's source and where. One function does it, called from the span rule, so no place is missed. The converter is our own, a pure function over a closed subset of TeX, 70 commands (`FORMULA_COMMANDS`, version `FORMULA_VERSION`, now `2`, named in the run line as `own-subset-2 (70 commands)`): 37 Greek letters (the 11 capitals are upright, `mathvariant="normal"`, as TeX sets them), `\le \ge \leq \geq \ne \neq \pm \cdot \infty \dots \mid \lceil \rceil`, `\sum \prod \int`, `\ast` (the star's synonym: the same `<mo>∗</mo>` as `*` in every position, so `\chi^{\ast}` and `\chi^{*}` give the same MathML), `\max \min \log \cos`, `\bar`, `\mathrm`, `\operatorname`, `\bigl \bigr \big`, `\mathbb` and `\mathcal` for a closed list of letters, and the four spacing commands. `\mathbb{X}` and `\mathcal{X}` (one letter, in a group or braceless like `\bar`) are the Unicode letter itself in a plain `<mi>` with no attribute, for exactly the letters the notes use: `\mathbb` C, F, Z (U+2102, U+1D53D, U+2124; F has no code point in the Letterlike block, so it is the one in the mathematical alphanumeric block) and `\mathcal` H (U+210B); any other letter, or more than one, leaves the formula unsupported. The output is MathML Core only: no script, no annotation, no outside asset. The page CSS gives a lone `<mi>` `text-transform: none; font-style: italic` (and `mathvariant="normal"` upright), because a browser's default math-italic mapping needs glyphs no common font has. A formula wider than its line scrolls inside itself instead of widening the page: `math { max-width: 100%; overflow-x: auto; overflow-y: clip; ... }` (the first three declarations of the rule; the rest of it is the continuation cue, the next paragraph; no new element, no attribute). The vertical axis is `clip` because with `auto` the engine draws a scroll control beside every short formula. Measured in a headless Chromium at a 390 px window on the real page: the page's `scrollWidth` was 428 before the rule, wider than the `clientWidth` (375 in a 2400 px high window, which has a scrollbar; 390 in a window as tall as the page), and after the rule it equals the `clientWidth` (375, and 390 in the tall window); with every Evidence section open it was 475 before and equals the `clientWidth` after. The window is 390 px wide throughout; 390 is not a page width the rule produces. At 1280 px the only change in a full-page screenshot is 235 pixels (the right overhang of an italic letter is clipped by the formula's own box). Only Chromium was measured. Formulas are taken out before the bold marks are read, so `$x**2 + y**2$` is a formula and `**$x$ holds**` is bold around one.

**The browser cases are run by hand only until they use a debugging pipe.** They open a DevTools port on the local machine for the length of the test, so they have no schedule, wrapper or CI job; the fixture they load is static and holds no script, which is what makes this tolerable today. Before anyone is expected to run them routinely, the launch moves to a debugging pipe.

**A cue that a formula continues (F51).** A formula wider than its box scrolls inside it, and a phone draws no scrollbar until it is touched, so the page shows, with no interaction, that the formula goes on: a soft shadow on the cut side only (on the right edge while there is more to the right, on the left edge while there is more to the left, on neither for a formula that fits, and the one on the right is gone when the scroll reaches the end). It is CSS only, in the same `math` rule: no element, no attribute, no script. It is the known scroll-shadow technique: two shadows with `background-attachment: scroll` are fixed to the box's left and right edges, and two covers with `local` move with the content and sit at its two ends, so a cover hides a shadow wherever the content does not continue (a formula that fits has both covers over both shadows). The rule is the wording file's, written into the `CSS` constant by script and not retyped. **The page has no colour of its own for it:** every colour is `Canvas`, `CanvasText` or `transparent`, the reader's own system colours (the shadow is 35% of `CanvasText` over `Canvas`), so the cue follows the reader's scheme with no branch (F51COL reads the rule token by token and refuses a hex colour, `rgb(`, `hsl(`, a named colour or a backslash, since a CSS escape can spell a colour name). The page declares no `color-scheme` (F51TEXT), so it is light today. **Measured** in a headless Chromium (Chrome for Testing 156, headless shell) at 390 px on the real page with every `details` open (a copy): 337 formulas, 9 overflow and 328 fit (the wording file measured 10 and 327 in Chromium 148; the difference is not explained and the numbers are not forced). Against the same page built with the old one-line rule (the formula's own ink is in both), the cut-side strip of the last 0.75em is darker by a mean luminance of 31 to 44 (of 255) on 8 of the 9 at the start (right edge) and at the end (left edge), and the other edge by 0.5 to 0.7; a formula that fits is within -0.3 to 2.6 on both edges. **The ninth overflows by one pixel (scrollWidth 291, clientWidth 290) and shows nothing visible** (drop 1.2): the cover is solid for the first 30% of its 1.5em, so, from the rule's geometry, the shadow appears once the content hangs over by about half an em (only the one-pixel case was measured). That is the technique's own limit. On a copy that declares `color-scheme: dark` the cut-side strip is lighter by up to 40 and the page background is 18, the mirror of the light case; the binary accepted no flag that forces the dark preference (four were tried), so the preference itself was not exercised. **Not measured:** Firefox, Safari, and a forced high-contrast mode. **To run the browser case:** `RH_CHROME=/path/to/a/headless/chromium python3 tools/build_site.py --selftest --only F51BROWSER`. The case is SKIPPED, with the reason, when the variable is not set to a file; the self-test reads no other path of the host. It builds a fixture page (2 long formulas that overflow at 390 px and 4 short ones that fit, in an argument), opens a copy with every `details` open, and for every `<math>` measures by pixels: a screenshot of the page with the new rule and one with the old rule, at the start and with every overflowing formula scrolled to its end, decoded with `zlib` and `struct`; a strip counts as darker at a mean drop of 10 or more and as not darker below 5. The browser is started with `--no-sandbox` and a profile in a temporary directory.

A formula outside the subset (an unknown command, `\frac`, an environment, an unbalanced brace, a backtick or a dollar sign inside, a character the tables do not hold) stays as written, whole, and is listed as `FORMULA-UNSUPPORTED <where> <the first 40 characters of the formula, marks included>`; `$$...$$` is not converted and is listed the same way. An unescaped `$` with no partner on its line stays literal and is listed as `FORMULA-UNPAIRED <where>`; `\$` is a dollar sign. `<where>` is a block id, or the group id for a claim, its conditions and the recognition, or the note id for a list title. **On the reader's surface a formula the converter cannot convert refuses the build** (`FORMULA-RAW`, exit 1, nothing written): an unsupported formula, a `$$...$$` and an unpaired `$` outside the Evidence section of a card, in every author-text place rendered through the span rule: a claim, a condition, a premise's claim, the recognition's text, the first sentence of an argument, a sketch, a note's list title (the first sentence and the titles of the notes about the whole too). The first screen and the key are strings of the strings file, not author text: they are not converted, never refused and never listed as unsupported; only the candidate listing below covers them. The error names the place, the first 40 characters of the formula as written (an unpaired `$` shows `$`) and where the author wrote it: for a block, the note file and the line of the block's anchor; for a note's list title, the note file; for a claim, a condition or the recognition, `outline/outline.json` and the group id. The place is found from the id alone, looked up as a block id, then a note id, then a group id: a group whose id is also a note id is named by the note file (documented limit, case `FRW7`); the checker refuses a repeated id of one kind but not across kinds, and the ids of this project's notes and outline do not collide. The same formula inside Evidence is only listed (`FORMULA-UNSUPPORTED`, `FORMULA-UNPAIRED`, exit 0). `\$` and a formula inside a code span are not formulas and are never refused. A listing never changes the exit code; only `FORMULA-RAW` refuses. The run prints `formulas: N converted, U unsupported, P unpaired, of T marks, converter own-subset-V (K commands)` after the sketches line; the counts are of renderings (the card's first sentence and the evidence text both count), and N + U = T is asserted (`FORMULA-SUM`, T counted from the marks the scanner finds), and N is compared with the number of `<math>` elements on the page (`FORMULA-PAGE`, exit 1 on a mismatch: a place that renders a formula without logging it is caught on the output). Known limit: the link pass runs before the formulas, so text shaped like a link inside a formula (brackets, then parentheses, as `$a [b](c) d$` or `$[a](b)$`) is read as a link first: the formula is converted from what is left and a spurious `LINK-OUTSIDE` is listed. For the same reason a listing line (`FORMULA-UNSUPPORTED`) and a `FORMULA-RAW` error show the formula after the links were taken out, not as the author wrote it (`$\foo [b](c) d$` shows as `$\foo b d$`; case `LIM-LINK2`). No formula of the notes has the shape; a formula that needs such text uses another notation. The JSON keeps every text as written. The first sentence is not cut at a full stop inside a formula. The source check also compares each text with its `$` marks removed and with the text of its MathML, so a release line wrapped in `$...$` or spelled out in a formula's letters is a leak.

Choices of the converter, pinned by cases: a letter is `<mi>`; digits with one decimal point are one `<mn>`; `+ - = < > / ( ) [ ] , ; : ! | . *` are `<mo>` (the minus is U+2212, `*` is U+2217; a fence or a bar has `stretchy="false"`, a bracket also `form`, because in a flat row a stretchy fence grows to the tallest sibling of the row); `\sum \prod \int` take limits in line (`msub`, `msup`, `msubsup`) and `\infty` is `<mo>`, as F26B says; a script is ONE token or one brace group, so `x^10` is x to the 1 followed by 0; a prime is U+2032 inside the token of a one-token `<mi>` base (`L'` is `<mi>L′</mi>`, `\zeta'` is `<mi>ζ′</mi>`, `f''` is `<mi>f′′</mi>`; capital Greek letters and function names keep their normal variant), because a headless-Chromium look at 1x and 2.2x showed a separate flat `<mo>` sitting in the top stroke of a zeta (gone at 1x) and an `msup` floating it high and apart; a base that is not a one-token `<mi>` (a number, a fence, a group) keeps a flat `<mo stretchy="false">′</mo>`; a script after a primed base starts with a thin `<mspace width="0.15em">` so the prime and the script do not run together (`r'^{-k}`); a prime after a superscript, a second superscript and a prime with no base are unsupported; `\bar` takes one token or one brace group (`\bar\chi`, `\bar{\chi}`) and gives `<mover accent="true">` over a stretchy U+2015 (a full-width overline; the macron and U+203E render tiny or partial); the `|` signs of one group (the formula or a brace group; parentheses are flat in it) pair in order of appearance, the first `form="prefix"`, the second `form="postfix"`, both non-stretchy, an odd leftover stays a flat non-stretchy `<mo>`; `\mid` and `\big|` are not paired bars; `\mathrm{..}` and `\operatorname{..}` give one `<mi mathvariant="normal">` per word and take scripts; after `\operatorname{..}` and `\max \min \log \cos` (the function-like commands; `\mathrm` is text, not a function), and after their scripts, a thin `<mspace width="0.167em">` is added when the next token of the same group is an identifier, a number, a group, a Greek letter, `\infty`, `\sum \prod \int`, `\bar` or another function (TeX's rule), and not before a fence, an operator, a relation, a prime, a script or an explicit space, nor at the end of a group; `\bigl \bigr \big` give the delimiter alone (no size); `\,` `\;` `\ ` `\!` give an `<mspace>` of 0.167em, 0.278em, 0.222em and -0.167em (pandoc's widths; `width` is the one attribute the allow-list lets through on `mspace`), a plain space gives nothing; an empty group is an empty `<mrow>`; a literal non-ASCII letter is `<mi>`, a symbol or punctuation mark is `<mo>`, any other non-ASCII character makes the formula unsupported.

**Two listings over the built page (S2, S3).** Both read the page with `html.parser` and look only at what is outside the Evidence section of each card. `FORMULA-CANDIDATE <card id> <rule> <the first 40 characters of the text node>` lists a text node that may hold a formula nobody marked with `$`: a caret (`caret`), an underscore then `{` (`underscore-brace`), a backslash then a letter (`backslash-command`), and the three marks the converter does not take, `\(` (`paren-form`), `\[` (`bracket-form`) and `\begin{` (`begin-form`, which is also a `backslash-command`). Text in a code span, in `<math>`, `<style>` or `<script>` is not looked at. No rule matches `\$` itself (a backslash then a dollar sign), so a text node with only that is not listed; a text node that holds `\$` and a caret is listed for the caret. (`\$` in author text is shown as `$`.) One line per card, rule and snippet; the card id is the nearest enclosing `<article>`, or `page` for the first screen. It is a listing and never changes the exit code. `CODE-ON-SURFACE <card id> <the text, first 60 characters> x<n>` lists the `<code>` spans outside Evidence and outside `<math>`, one line per card and text, `n` the occurrences in the card. The constant `CODE_ON_SURFACE_REFUSES` in `tools/build_site.py` is `False`: a span is listed and the build goes on. Set to `True`, any span refuses the build (`CODE-ON-SURFACE`, one line per card and text, exit 1). Flipping it is two edits: the constant, and the one literal of the self-test case CS1 that pins the value in the file; the rest of the self-test pins the constant to `False` for every case (CS5 sets `True` on purpose) and does not change. On the real notes a flipped build is refused with the 187 lines of the listing until those spans are gone from the notes. The run prints `formula candidates: C in K cards` and `code on surface: N spans (D distinct) in K cards` after the `formulas:` line (the listing has one line per card and text; `D` of the run line counts the distinct texts across the whole page, so it is never more than the number of lines).

**`tools/graph_js_check.py [DIR]`** is the grep gate for the graph view's shipped sources (default `viewer/graph/`): it refuses any file under it that contains `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `DOMParser`, `createContextualFragment`, `eval(`, `new Function`, `http:`, `https:` or a `setTimeout`/`setInterval` whose first argument is a string, and, in a `.html` file, an `on...=` attribute, `<style` or `style=`. A directory named `test` is not shipped and is not read. It prints `REFUSED path:line TOKEN` and `N files checked, M refused`; an empty tree prints `CHECKED NOTHING` and fails. It checks text by substring and line pattern, so a token split across lines or built from pieces is not seen, and a comment that names a token is refused too (the LIMIT in the file). `python3 tools/graph_js_check.py --selftest` plants each token in a temporary tree and expects its refusal.

**`tools/formula_oracle.py`** is a measurement, not a build step. It runs a list of formulas through our converter and through `pandoc -f markdown -t html --mathml` and compares the tag trees (attributes and text dropped, pandoc's `<semantics>` and `<annotation>` removed, an `<mrow>` around a single child removed), prints how many agree, and lists every formula that differs with a one-line reason and which side is right. It exits 0 after a completed run, whatever the number of differences; with pandoc missing from the PATH, a formulas file that cannot be read, or pandoc failing, it prints one line to stderr and exits 2. `python3 tools/formula_oracle.py --run FORMULAS_FILE [FORMULAS_FILE ...]` needs pandoc; `python3 tools/formula_oracle.py --selftest` does not (it uses a recorded pandoc output).

The run also prints `recognition: K known, V variant, N not recognised, O open in literature, M not written, of G groups with a claim` (all groups with a claim at every depth; refused as SUM-RECOGNITION when the counts do not add up) and `sketches: S of P steps with a proof read` (level-1 steps; SUM-SKETCH when S exceeds P).

The source check now also compares the recognition's result, difference, note, every citation's source and where, and every sketch paragraph, list item, unexpanded entry and unexpanded_detail entry as a reader sees them (and each link target as a line). The class of an anchor the static check lets through is a token of its class list: `class="citation extra"` and `class="reaction extra"` pass, `citationx` does not, and the citation exemption is for `href` alone (`xlink:href`, `action` and `formaction` to an address are refused). The strings file needs the recognition, established and sketch keys and `argument_frame_no_proof`; a rule of the strings check refuses the phrase `of the proof` in any value.

**Provenance is off the card (F37 a to c).** Who read what, and when, is for the maintainers and the authors, not for the reader of the card. No sentence of the card names a reader, a date of ours, a file, lines or a build: the statement and proof lines say `We have read this statement.` and `We have read this proof.` (or that we have not, or that a program counted the statement), the frames of the argument, the definition, the interpretation and the sketch name nobody (the sketch frame says its basis: `from reading the Lean source`, or `from the goals Lean shows when this part of the release is compiled`), a citation line is `{source}, {where}` (and `, dated {source_date}` for a source that says open on an open card; that date is the source's own), the established line is `Where it is proved: the release proves this statement as {name}.`, and the label line is one sentence, `No mathematician has checked our reading yet. ...`, shown once at the end of each recognition block (a card with the not-written line has none). The second readers' line is not on the card and not in the closed card's first sentence. What left the card is in the card's Evidence section, a `<details>` that is closed by default. In it, after the root blocks and before the list of blocks, `<ul class="provenance">` lists, in this order: the statement line (`evidence_statement_read_line`, or `evidence_statement_census_line` for a census claim; only on a card with one root or none, as on the card), the proof line (`evidence_proof_read_line`, from the first argument block), the recognition (`evidence_recognition_line`: its reader and date), one line per citation (`evidence_citation_line`: who opened it and when, the source through the span rule) and, for a named statement that was traced, `evidence_established_line`. In the list of blocks, after the text of a block: for an argument or sketch block `<dl class="block-source">` with the labels File (the base name) and Lines (the range; `not given` when the block has none, and also when it has no file, because lines name no file: the rule of F29), then one `<p class="second-reader">` per second reader of the block (`evidence_second_reader_line`; any kind of block), and for a sketch built from a compiled part of the release `<p class="sketch-build">` (`evidence_sketch_build_line`). A card with nothing of this to say keeps the Evidence section it had. The group files, the level files and `data.js` are unchanged: every reader, date, second reader, file and line range is still in the data. A correction block on a card shows its kind and its title (what was wrong stays visible); its reader and date are in the Evidence list of blocks, beside the block's kind.
