# Text tools for reading the Lean source

These are text tools; they find where to read, they do not prove a dependency. Python 3, standard library
only. Each one runs its own self-test first and refuses (exit 4) if it fails. `--selftest` shows the cases. In `notes_meta.py` a case id registered twice stops the tool at load with a message naming the id and both descriptions; ids are compared as exact strings, so `rec1`, `REC1` and `REC1 ` are three ids.

A run that checks nothing (no `.lean` file under SRC_ROOT) writes nothing. If OUT_DIR already holds a file that run
would have written, an earlier result looks like this run's to the next tool; so `scan_graph.py`, `alias_edges.py`
and `decl_table.py` print one more line after `CHECKED NOTHING`, `OUT_DIR holds files from an earlier run: <names>;
this run wrote nothing`, and keep exit 1. They do not delete the files.

For whoever writes the next self-test: **the expected value in a case is a literal, never read back from the tool.**
A case that computes its expectation with the code under test, or with a helper the tool exports, passes whatever
the tool does. Write the number, the line or the list into the case, and run a wrong version of the tool (a copy)
to see the case go red.

**`tools/scan_graph.py SRC_ROOT OUT_DIR`** answers: which files exist, how big, what do they import?
It writes `files.tsv` (one row per file, with word counts) and `edges.tsv` (one row per internal import).
`python3 tools/scan_graph.py SRC_ROOT OUT_DIR`

**`tools/alias_edges.py SRC_ROOT OUT_DIR`** answers: which theorems are only a wrapper around another
theorem, where is the target declared, and where are the names written out in full? It never picks
between two declarations with the same full name; it lists both.
`python3 tools/alias_edges.py SRC_ROOT OUT_DIR`

**`tools/decl_table.py SRC_ROOT OUT_DIR`** answers: which named declarations are in each file, on which lines?
It writes `decls.tsv` (module, name, kind, first line, last line, basis) and `decls_dup.tsv` (every row whose
module and full name occur more than once; it never picks one). The lines are the text rule's extent, not Lean's;
the rule lives in `tools/lean_decls.py`, which `alias_edges.py` also uses. `example` lines and instances with no
name are not rows; they are counted on the second summary line.
`python3 tools/decl_table.py SRC_ROOT OUT_DIR`

**`tools/rh_anchor.py`** is a small library, not a command: the one place that knows the anchor format of the
notes. A note carries its metadata in one-line comments, `<!-- rh-note {...} -->` (the header) and
`<!-- rh-block {...} -->` (a block anchor, on its own line after the paragraph, table or lean block it anchors),
so the rendered page does not change. The checker and the helper that writes anchors both import it. It reads and
writes the lines (`parse_note`, `format_comment`, `strip_anchor_lines`), says which element an anchor follows and
where a new one goes (`target`, `target_at`, `insert_after_line`; a new anchor goes at `append_after`, after any anchors already there), checks the shape of a block or header
(`problems`, `header_problems`, `block_id_ok`), reads the run of elements a `sketch` block covers (`run_at`) and numbers new ids (`next_block_id`). It checks shape only: not the
outline, not the declaration table, not whether a table row exists. Markdown is approximated by three rules (fences,
tables, one comment per line), not CommonMark; the LIMIT paragraph in the file lists what is not recognised.
`python3 tools/rh_anchor.py --selftest`

**`tools/notes_meta.py NOTES_DIR OUTLINE DECLS_TSV`** answers: is the metadata of the notes well formed, and does every
name in it resolve to one row of `decls.tsv`? It reads the outline (every group, its parent, level, order,
premises, roots and claim), each note's header and anchors, and, with options, more: `--src SRC_ROOT` checks that
a block's `file` is in the note's file table and its `lines` are inside the file, `--strings PATH` lists blocks
whose text opens with another kind's frame, `--base REV` checks that the note at REV and the current note, both with
their anchor lines removed, are equal byte for byte after that rule, except that text the note only GAINED as dated additions is listed, not refused (see below; this needs the `git` program; `--repo DIR` names the repository when it is not the one around
NOTES_DIR), `--today YYYY-MM-DD` sets the day the additions are checked against (a test hook; default the UTC date of the clock), `--glob PATTERN` changes which files are notes (default `[0-9][0-9]-*.md`, so this folder's
`tools.md` is not one). The format of the comments is read only through `rh_anchor.py`. A finding is one line,
`CODE path:line message`; `EXTENT-WARNING`, `FRAME-NOTE`, `NEW-NOTE`, `ADDITION`, `CLAIM-LIBRARY-WORD`, `ROOT-ROLE-MISSING` (while it is not required) and `RECOGNITION-WORD` are listings and never fail the run. Each
note prints `note <id> header ok, blocks N (kind=count ...)`, and the run ends with the counts by kind, what the
in-file and byte checks did or did not do, and `N notes, M findings, K warnings`. It checks shape and resolution;
it does not judge whether a claim is right, and the LIMIT paragraph in the file lists the title rules and the
translation rules that need a reader. Every group needs at least one root; a group with a null claim and no root passed
in the first version and is now a ROOT-COUNT error. The title rules the script applies are heuristics, named in the LIMIT. A dotted token (`Foo.bar`) or a CamelCase word (`getValue`) in a claim `text` or a `conditions` entry outside single backticks is listed as `CLAIM-LIBRARY-WORD` (once per token and text; a prompt to write it in backticks or in plain words, not a proof; the rule is exact in the LIMIT). A claim may carry `basis` (`read` or `census`), optional for now; a summary line counts the non-null claims that are objects by basis (a claim that is not an object is its own BAD-VALUE and is counted in none). A group may also carry two optional keys. `root_role` (`result`, `named_statement` or `object`) belongs to a claim, and the checker compares it with the kind of the group's root in `decls.tsv`: `result` if and only if the kind is `theorem` or `lemma`; every other kind (`def`, `structure`, `abbrev`, `inductive`, any other) takes `named_statement` or `object`; a mismatch is `ROOT-ROLE`. A claim with no `root_role` is a `ROOT-ROLE-MISSING` listing for now (the real outline has no roles yet) and an error once the constant `REQUIRE_ROOT_ROLE` is set to True. `recognition` says where we read the statement stands: a `form` (`known`, `variant`, `not_recognised`, `open_in_literature`), `reader` and `date`, and per form a `result` in plain words, `citations` (each with `source`, `where`, `opened_by`, `opened_on`, and optionally `url`, `source_date`, `says_open`) and a `difference`. The form `not_recognised` may also carry one optional `note`, a string that is not blank, saying what the step is in the release's own terms and what we looked for; on any other form with a known form `note` is `RECOGNITION-FORBIDDEN`, and `result`, `citations` and `difference` stay forbidden on `not_recognised`. The number of sentences in a note is not checked. It is refused on a null claim; `open_in_literature` is only for a `result` or a `named_statement` (on an `object`, or with no `root_role`, it is `OPEN-ROLE`; `established` stays for a named statement only), needs a citation with `says_open` true and its `source_date` (a year `YYYY`, a month `YYYY-MM` or a day `YYYY-MM-DD`, each a real date, validated here, and the page builder will print it as written; year 0 is refused; `opened_on` stays a full `YYYY-MM-DD`); the words `novel` and `unprecedented` in `result`, `difference` or `note` are an error, and `new`, `original`, `first`, `assume`, `assumes`, `assumed` are listed as `RECOGNITION-WORD` (a prompt to the signer and the reviewer, not a proof; a word inside single backticks is checked too). A named statement may carry `established`: `not_traced`, or the theorem or lemma (`by`, which must resolve to one row of that kind) with its reader and date; that its conclusion is the named statement is the reader's claim. The run prints `recognition: K known, V variant, N not recognised, O open in literature, M not written, of G groups with a claim` after the `claim basis:` line, counted by the tool and asserted to add up (`SUM-RECOGNITION`). The check of these fields against the lines of the release is the builder's, not this tool's. A `sketch` block (a reader's short account of a proof, written after the idea) carries `reader`, `date`, `decls`, `basis` (`source` or `compiled`; `compiled` needs a `build` string and `source` refuses one), and optionally `unexpanded` (a list of strings) and `span` (an integer of 1 or more, default 1: how many elements, ending at the one the anchor follows, the sketch covers). Only a sketch may carry `span`, and a sketch carries no `item`. The run may hold paragraphs and lists; a table, a fence, a heading, a quote, an HTML line or another anchor inside it is refused, and so is a span larger than the elements between the anchor and the previous anchor, heading or the start of the note. A block belongs to the group named in its note's header and anchors a root of that group when its `decls` include the root; the counts run over all the notes of the group. The checker refuses a sketch whose root has no argument block (`SKETCH-NO-ARGUMENT`), a second sketch on one root (`SKETCH-DUPLICATE`, naming both block ids), a sketch on a root that is not a result (`SKETCH-ROLE`: the group's `root_role` when it has one, else the kind in `decls.tsv`, theorem or lemma; each root of a null-claim group by its own kind), a sketch whose `decls` hold no root of its group (`SKETCH-ROOT`), and a span the run cannot cover (`SKETCH-RUN`, with the reason from `rh_anchor.run_at`). An argument block anchored on a root whose kind is not theorem or lemma is listed as `ARGUMENT-NO-PROOF`: a prompt to the reader, since a definition can carry small proofs inside; it never changes the exit code. The note line and `blocks by kind:` count seven kinds. The line `sketches: S of P steps with a proof read` is not printed by this tool: what a step is belongs to the builder, which counts it. `note_cite.py` is unchanged: its `--kind` takes the kinds from `rh_anchor`, but it has no flag for `basis`, so a sketch cannot be valid through it and is refused as `BAD-BLOCK`. Two notes whose headers carry the same `id` (exact strings, first header of each note) are `NOTE-ID-DUPLICATE`. **Dated additions.** A note may gain text after publication without a byte difference when every base line is still there, unchanged and in order, and each run of new lines begins, after any blank lines, with a heading (one to six `#`, a space, text) whose text holds a real date `YYYY-MM-DD`. The base is matched into the current text from the left (a repeated line is taken at its first match) and, if that leaves an illegal run, from the right (taken at its last match); the note is accepted when either gives only legal runs, and the runs of the first that does (left first) are listed. Two alignments are tried, not every possible one. Every real date in the heading may not be later than the day of the run and may not be earlier than the date in `release` of the note header **as published** (the text at `--base`, so editing or deleting `release` since then does not lower the limit) when that is written `rh-YYYY-MM-DD`; a published release with no date, or an impossible one such as `rh-2026-02-30`, gives no earlier limit, and the limit is the release's date, not the note's own. A run may not touch published text: the line before its first non-blank line and the line after its last one must each be blank or the edge of the note (a blank line inside the run counts; anchor lines are not text), otherwise it is a byte difference naming the run and the side; a run above the first published non-blank line (above the title) is one too. Fence state is kept: a published line that is inside a fenced block in one text and not in the other (an inserted marker that wraps published text in a code block, or ends a published block early) makes the note a byte difference, and the message names the inserted run. Each such run is printed as `ADDITION path:LINE N lines, heading TEXT` (the line in the file as it is on disk, N the lines of the run), is counted among the warnings, and never changes the exit code; the byte-check line ends `additions A`. Everything else stays a byte difference: a removed or altered base line, a run with no dated heading first, a date outside the window (the message names the date and the window), an impossible date such as `2026-13-45`, and a run inside a fenced block of the published text. One run that fails makes the whole note a byte difference. Two limits: a line that repeats an earlier base line can leave the original unmatched as a second run on both alignments, which then fails unless it is itself a dated addition; and a note whose last line has no line ending cannot gain text after it. The boundary rule looks at blank lines only, so a run that brings its own blank line on each side and sits between two table rows, or inside a list item, is accepted and splits that table or list. A byte difference is reported at its line in the current file as it is on disk (and its index without anchors), so a reader opens the file at that line; where text is missing from the current file the number points past the end of the text: the line after the last non-anchor line, which is an anchor line when anchors trail it and otherwise one past the last line of the file (not a line that exists), or 1 when the file has no non-anchor line. The strip rule is `rh_anchor`'s: a last anchor line with
no line ending of its own also removes the line ending before it, so adding or removing such a hand-typed last line can read as a
one-line-ending difference; anchors written by the helper carry their own ending. An anchor-looking line counts as text only inside
a fence, and a malformed `rh-` line is kept as text, so fixing it since REV is a byte difference. A block anchored to a list must name its top-level
item (`item`, 1-based, counted across blank lines: a loose list is one list; nested items are not numbered), except a `sketch`, which covers whole elements, a list included as a whole: a sketch whose target is a list is not asked for `item`, and `item` on a sketch is a block problem (`BLOCK-PROBLEM`, with none of the other item findings beside it); shapes of list a renderer may show differently are refused through a table
that is empty until the renderer control is in, for the anchored list of any block and, for a sketch, for every list in its run (a list that is not the target is named with its first line; a sketch with a bad span or an illegal run gets that finding and no shape finding). Limit: the shape keys `last_nested` and `followed_by_paragraph` describe an anchor adjoining a list, and no anchor follows a list in the middle of a run, yet the table is applied to every list as written, so whoever fills the table decides whether those two keys apply to a list that is not the target. The run prints a count line for the outline (and for the strings file and the
byte check when they ran); a header's group may be `root` only at level 0.
`python3 tools/notes_meta.py NOTES_DIR outline.json decls.tsv [--src SRC_ROOT] [--strings strings.json] [--base REV] [--today YYYY-MM-DD]`

**`tools/note_cite.py NOTE DECLS_TSV --at LINE --decl FULL.NAME --kind KIND`** writes one block anchor, so nobody
types the JSON. It finds the declaration's module in `decls.tsv` (`--module` picks one when the name is in several),
takes the element of the note that holds line `--at` (a paragraph, table, list or lean block, or the anchor lines just
after one), and puts the comment after that element and after any anchors already there, so a second anchor on one
element lands below the first. For a table it fills `row` (and `col` if given), for a list `item`, from the line or
from `--row`/`--item`. It refuses, with one line `REFUSED CODE message` and nothing written, when the name does not
resolve to one row, when `--lines` cross the declaration's text extent, when the file is not in the note's file table,
when the line is in a heading, quote or non-lean fence, when the note has no header or a comment the parser cannot
read, when a kind that needs `--reader` and `--date` lacks one (it never fills either by default, and an empty value is
refused too), and when a flag belongs to another kind (`--needs` outside `not_read`, the tool fields outside
`machine_fact`: STRAY-FLAG). The block is
checked with `rh_anchor.problems` before it is placed, and the result with the same parser the checker uses: the note
without its anchor lines must not change. By default it only prints the comment and the line it would go after;
`--write` writes the note, keeping its file mode, and through a symlink writes the link's target. `--src SRC_ROOT`
(with `--lines`) also prints the cited lines from your local copy of the release, so you see the statement while you
cite it. It does not judge whether the cited lines support the sentence, or whether the kind
is right: that is the reader's and the peer's job, and `notes_meta.py` is the check of what it writes.
`python3 tools/note_cite.py docs/13-how-the-sha-bound-is-used.md decls.tsv --at 214 --decl UpperTheory.Top.topDesWin --lines 25-25 --kind reading --reader NAME --date YYYY-MM-DD --src SRC_ROOT`

**`tools/build_site.py NOTES_DIR OUTLINE DECLS_TSV STRINGS OUT_DIR`** answers: what do the first two zoom levels
of the proof map look like, built from the notes, the outline and the declaration table alone? It first runs the
check of `notes_meta.py` on the same inputs (its library function, not a subprocess) and refuses to build, writing
nothing, not even OUT_DIR, if that finds an error. Then it writes, under OUT_DIR: `level0.json` (the steps of the
chain in `order`, the counts of the two facts, the notes about the whole, the number of open questions), `level1.json` (each step with its child groups
nested under it to any depth), one `group/<id>.json` per group (its `premises`, its roots with file, lines and, with
`--source-check`, the hash of the file, and per root the two facts `statement_read` and `proof_read`; the blocks that anchor them; the open `not_read` items), `manifest.json`
(the hash of every other file, the three commit ids, the release id and archive hash, the counts), `data.js` (the
same data as one assignment) and `index.html`. The page is one static file of plain HTML: each step is a card (claim,
conditions, premises as links (for a step with a null claim too), two status lines, a line counting the open questions (on a card only above zero; the first screen always says it), the first sentence of the argument inside
its frame (rendered by the span rule below), three reaction links; a span between single backticks on one line in a claim, a condition, a note's title or the text of an argument or interpretation block is shown as code, by the same span rule `notes_meta.py` uses, and nothing else in them is markup; block text is one paragraph joined by spaces first, so a span over a source line break is a span, and formulas in it are not converted), evidence is a closed `<details>`, child groups open in place, and nothing on it needs JavaScript or
makes a request. Every FIXED sentence on the page comes from the strings file, whose shape is provisional (the fixtures of the self-test carry their own wording, not the real one; the keys for the status
lines are provisional names, the owner of the wording may rename them: `statement_read_line`, `statement_census_line`,
`statement_not_read_line`, `proof_read_line`, `proof_not_read_line`, `proof_not_applicable_line`, `proof_none_other_line`, `steps_proof_not_applicable_line` (no placeholders in these three), `statement_count_line`, `proof_count_line`,
`open_items_line`, `steps_statement_line`, `steps_proof_line`, `steps_open_items_line`, besides `no_claim_label` and the three labels of the evidence block, `evidence_module_label`, `evidence_name_label`, `evidence_kind_label`); a
missing key stops the build and names itself, and a stale key (`coverage`, `not_read_yet`, `roots_not_read`, any other
top-level key, or key directly under `labels`, whose name holds `not_read`) is refused. There is no coverage word. Per root there are two facts: the statement is
read when the group's claim has basis `read` (a claim without a basis counts as `read` until the checker requires one) or
a reading block anchors the root; the proof is read when an argument block anchors it, and only a root that has a proof can have it read: the kind column of the declaration table decides, `theorem` and `lemma` have a proof and every other kind (a definition, a structure, an instance, an abbreviation, a class, an inductive type) has none, so an instance or a definition with a proof term does not count as having a proof for the page. For such a root the proof fact is not applicable (`null` in the JSON, never `false`), and the card shows `proof_not_applicable_line`. A kind that is none of the eight the table holds, or is empty, is treated the same way, the card shows `proof_none_other_line` instead (also for a step with several roots when ANY of its proof-less roots has such a kind), and it is listed as `KIND-NOTE <group> <module>.<name> kind '<kind>'`. A claim of basis `census` does not
count. A step counts for a fact when every root of it has it (for the proof, every root that has a proof: the definition roots of a step are left out of that test, and a step none of whose roots has a proof counts as not applicable; the card counts over the roots that have a proof; a group with no root is never counted as read; that guard is redundant by
design, the checker refuses such a group first). The build asserts read + not read = total for the statement and read + not read + not applicable = total for the proof, and prints the numbers; these sums guard a
MISSING flag, not a WRONG one. The first-screen proof line counts over the steps that have a proof, and when no step has one it shows `steps_proof_not_applicable_line` in its place (the first screen does not distinguish an unknown kind; none is reachable among top-level steps on a real table). For a null claim or a census claim the statement reader is the first reading block of the root by
note id and then block number, not by date.
A group whose claim is null shows its root's Lean name and the `no_claim_label` in the heading, then the status lines.
Open questions are the distinct open `not_read` blocks, each counted once. Since F37 the proof line and the statement line of the card say the fact and name nobody; the
Evidence section names the reader and date of the first argument block of the root, by note id and then block number (the rule of the
statement reader, not by date). Every value of the
strings file, at any depth, may hold only the `{placeholders}` its key declares (`evidence_proof_read_line` declares `{reader}` and `{date}`; `proof_read_line` declares none);
an undeclared one is refused naming the key and the token, the keys that must hold every placeholder they declare are refused when a value lacks one (the count and open-items lines named above, the recognition and citation lines, `established_by_line`, `sketch_frame` and the eight Evidence keys of F37; `shared_note`, `note_href` and the reaction hrefs may omit theirs; the refusal names the key and the missing placeholder), a key that declares none may hold no brace, and a new key
is covered by default. The build also stops for: the words
verified, explained, understood (or any word of `forbidden_words`), a percent sign or `of the proof` in the strings file
(the builder's own sentences never contain them; its href templates may hold `%`; the words `Read by us`, `Partly read`
and `Not read yet` are refused too, the scale is gone; that match is exact-case and single-space, so the lowercase phrase
`not read yet` is allowed inside status wording); a reading, argument,
interpretation or correction block with no reader or no date; a fact whose read and not-read counts do not add up to
the total (SUM-STATEMENT, SUM-PROOF); a reaction target that is not an https URL (the hrefs may hold any word, a label
may not); a link on the page with no target; a number
on the page that is in no JSON file; a group id that is not safe as a file name. `--source-check SRC_ROOT` compares
the text lines of every output (what a reader sees: the backticks of a span are removed from claim text, conditions, note titles, block text and a block's first sentence first, on the JSON side; the page itself is not compared inside `<code>`), and the source lines of every copied note text (an argument or interpretation
paragraph, a note title) before they are joined, with the lines of the release (at least 20 non-space characters), and
says what it ranged over; names and ids are left out by construction. What it shows is narrow: no output line equals a
release line and no line of copied note text equals one; a release line quoted inside a longer sentence (of a claim, of block text or of a first sentence) is not
detected. Block text and a block's first sentence are compared both as written and with span backticks removed, so a release line that itself holds a span is still seen there. The first sentence of an argument block is cut at the first `.`, `!` or `?` followed by white space even inside a span (a span holding `f. g` gives the sentence ending in `f.`, its backtick left literal on the card): a known limit, not changed. `--notes-commit REV --repo DIR` stamps the notes commit; a
tree whose notes, outline or strings differ from it, or whose tools differ from their commit, stamps `dirty` in every
commit id and on the page. A fresh run into a non-empty OUT_DIR refuses unless `--force`, which removes only what a
build writes. The site is written into a temporary directory beside OUT_DIR and renamed into place, so a failure
leaves OUT_DIR absent or the old build as it was; a failure to write is exit 2 with one line. Text from the notes and
the outline (claims, conditions, note titles, argument and interpretation text) is not refused for those words: each
hit is listed as `WORD-NOTE <where> <word>` on stdout, the exit code is unchanged and the text is never edited. A block whose argument, interpretation or sketch text (a sketch's paragraphs and list items), outside its single-backtick spans, holds `$`, `\(`, `\[` or `\begin{` is listed as `FORMULA-RAW <block id>` (once per block, in note order, after any KIND-NOTE lines): exit unchanged, nothing written. Blocks of other kinds, and a sketch's `unexpanded` entries, are not scanned. It is a mark detector, not a formula parser (a dollar amount is listed too), and a formula inside a code span is not; formulas are not converted yet (F26 will). For
`of the proof` the listing is narrower than the refusal in the strings file (which takes any occurrence): in the notes'
text only a number, a percent sign or a quantity word (half, third, quarter, most, part, fraction, portion, share,
majority, all; the list is provisional) immediately before it is listed, so a title like `the top of the proof` is not. The recognition, the sketch and the frame of a block (F24b, F25b, F29, F30, F31). A group's `root_role`, `root_kind` (the table's kind of its one root) and `recognition` (as written in the outline) are carried by the group file and the step summaries (null for a group with no claim; never inside `counts`); the group file also has `sketches` (one entry per sketch block: note, block, reader, date, basis, build, unexpanded, roots, and its paragraphs and lists as written). A card with a claim shows, after its premises line and before its status lines, the recognition block: the form line for its role and form (a group with no `root_role` takes the class of its root's kind: theorem or lemma, result; any other, named statement; a recognition the checker refuses may stop the page), the difference, one line per citation (an https `url` makes the line an `<a class=citation>`, the one external anchor besides the reaction links), the `established` line of a named statement, and the label line; for a `not_recognised` form the `note`, when there is one, comes after the form line (span rule only, links are not rewritten there). With no recognition the not-written line shows. An open form prints the newest `source_date` among the citations that say open, compared as strings as written. Every named-statement card also shows the named-statement line, directly after its claim and conditions and before the premises line and the recognition block (also when the recognition is not written).

After the argument the card shows the sketch (its frame, paragraphs and lists, the unexpanded places, the note that it is a sketch), or, when its proof is read and it has none, the missing-sketch line; a sketch never sets `proof_read`.

An argument block anchored only on roots that are not a theorem or a lemma is framed by `argument_frame_no_proof`; the not-applicable proof line stays and `proof_read` stays null. Since F37 the frame holds no file and no lines (`argument_frame` and `argument_frame_no_proof` declare no placeholder): the base name of the block's file and the range of its lines are in the Evidence section, with the second readers' lines (see below).

In the text of an argument, interpretation or sketch block a markdown link `[text](target)` is shown as its text and makes no anchor (an image, a link in a code span, a target with a space and a bare bracket pair are left as written); the run prints `links in block text: N shown as text` and `LINK-OUTSIDE <block id> <target>` for each target that is not a note of the build (a listing only).

In the same text (the first sentence of an argument block too, not a claim, a condition, a title or an `unexpanded` entry) a pair of double asterisks on one line around text is shown as `<strong>`, its content through the span rule, so a code span may sit inside it; an asterisk in a code span is code, and single asterisks and underscores stay text. An empty pair, a pair of blanks, a run of three or more asterisks and a pair over a line break that is still there after the paragraph join stay as written (a paragraph, an item and argument text have their source lines joined by spaces first, so a pair over a source line break there is bold, as a code span is). A `**` that is no pair stays literal on the page and is listed as `BOLD-UNPAIRED <block id>` (once per block, after the FORMULA-RAW lines; a listing only). In a sketch, the indented `- ` or `* ` lines of a list item are its sub-items, shown as one nested `<ul>` inside that item's `<li>` (the text before the first sub-item stays the item's own); a deeper level is shown flat and listed as `NEST-DEPTH <block id>`, and an indented numbered line is a continuation line. In the sketch's JSON an item with sub-items is `{"text": ..., "items": [...]}` and every other item is still a string. The source check compares the text with its asterisks removed, as it does for backticks. The page CSS holds `code { overflow-wrap: anywhere; }` so long code wraps on a narrow screen. `<strong>` and a nested `<ul>` are the new elements the builder emits; the static check looks for requests and has no list of allowed elements.

The built page is also checked against one list of the elements it may hold, and the attributes of each (`ALLOWED_ELEMENTS` in `build_site.py`: 41 elements and 49 element-attribute pairs). The list is the 29 elements the builder emits today, measured over the self-test fixtures and a build of the notes of this repository, and the 12 MathML elements the formula converter writes (`math mrow mi mn mo msub msup msubsup mover munder munderover mspace`, with `mathvariant`, `stretchy` and `form` on those only). An element or an attribute outside the list (a `<script>`, an `<annotation>`, an `<iframe>`, an `onclick` on a `<p>`, an `href` on a MathML element, a `style` where the builder has none) is refused as `PAGE-STATIC element <name>` or `PAGE-STATIC attribute <name> on <element>`, exit 1, nothing written, the same code as the other static findings.

The run also prints `recognition: K known, V variant, N not recognised, O open in literature, M not written, of G groups with a claim` (all groups with a claim at every depth; refused as SUM-RECOGNITION when the counts do not add up) and `sketches: S of P steps with a proof read` (level-1 steps; SUM-SKETCH when S exceeds P).

The source check now also compares the recognition's result, difference, note, every citation's source and where, and every sketch paragraph, list item and unexpanded entry as a reader sees them (and each link target as a line). The class of an anchor the static check lets through is a token of its class list: `class="citation extra"` and `class="reaction extra"` pass, `citationx` does not, and the citation exemption is for `href` alone (`xlink:href`, `action` and `formaction` to an address are refused). The strings file needs the recognition, established and sketch keys and `argument_frame_no_proof`; a rule of the strings check refuses the phrase `of the proof` in any value.

**Provenance is off the card (F37 a to c).** Who read what, and when, is for the maintainers and the authors, not for the reader of the card. No sentence of the card names a reader, a date of ours, a file, lines or a build: the statement and proof lines say `We have read this statement.` and `We have read this proof.` (or that we have not, or that a program counted the statement), the frames of the argument, the definition, the interpretation and the sketch name nobody (the sketch frame says its basis: `from reading the Lean source`, or `from the goals Lean shows when this part of the release is compiled`), a citation line is `{source}, {where}` (and `, dated {source_date}` for a source that says open on an open card; that date is the source's own), the established line is `Where it is proved: the release proves this statement as {name}.`, and the label line is one sentence, `No mathematician has checked our reading yet. ...`, shown once at the end of each recognition block (a card with the not-written line has none). The second readers' line is not on the card and not in the closed card's first sentence. What left the card is in the card's Evidence section, a `<details>` that is closed by default. In it, after the root blocks and before the list of blocks, `<ul class="provenance">` lists, in this order: the statement line (`evidence_statement_read_line`, or `evidence_statement_census_line` for a census claim; only on a card with one root or none, as on the card), the proof line (`evidence_proof_read_line`, from the first argument block), the recognition (`evidence_recognition_line`: its reader and date), one line per citation (`evidence_citation_line`: who opened it and when, the source through the span rule) and, for a named statement that was traced, `evidence_established_line`. In the list of blocks, after the text of a block: for an argument or sketch block `<dl class="block-source">` with the labels File (the base name) and Lines (the range; `not given` when the block has none, and also when it has no file, because lines name no file: the rule of F29), then one `<p class="second-reader">` per second reader of the block (`evidence_second_reader_line`; any kind of block), and for a sketch built from a compiled part of the release `<p class="sketch-build">` (`evidence_sketch_build_line`). A card with nothing of this to say keeps the Evidence section it had. The group files, the level files and `data.js` are unchanged: every reader, date, second reader, file and line range is still in the data. A correction block on a card shows its kind and its title (what was wrong stays visible); its reader and date are in the Evidence list of blocks, beside the block's kind. Not covered: what an author writes in a note's text or sketch is the author's. The strings file holds the eight Evidence keys, and `second_reader_frame` is gone; the argument detector `frames.argument` is `How this is proved`, so a note whose own text opens with the frame is still listed as FRAME-NOTE.
A `not_read` block in a level-0 note is anchored to no group: it is not counted in the number of open questions and is shown on no
card. The

**`tools/in_closure.py EDGES_TSV START_MODULE SITES_FILE --control MODULE`** answers, per site: is this
file compiled before the start module (INSIDE, with one shortest import path) or not (OUTSIDE)? Give at
least one control, a module you know is inside; if a control is not, the run stops and says BROKEN.
`python3 tools/in_closure.py OUT_DIR/edges.tsv Some.Start.Module sites.txt --control Some.Known.Module`

**`tools/import_closure.py`** is the size-and-folder summary of one closure. `in_closure.py` answers the
per-site questions. Both read the import lines through the same header reader in `scan_graph.py`, so they
agree on what a header is.

The header reader ends the header at the first line that is not blank, `import`, `module` or `prelude`, so Lean's `public import` and `meta import` forms would end it early and hide what follows (none was found in the release read; a later release must be checked).

Every TSV starts with one `#` line (what was read, the source commit, what a row is NOT), then the column
row. Exit codes, tool by tool (4 always means the self-test failed and nothing was reported):

- `scan_graph.py`: 0 clean; 1 an unresolved import under a folder of the root, an undecodable or unreadable file, or no `.lean` file; 2 usage error or SRC_ROOT not a directory.
- `alias_edges.py`: 0 even when unresolved or ambiguous targets or odd-shape rows are printed; 1 only for an undecodable or unreadable file or no `.lean` file; 2 usage error or SRC_ROOT not a directory.
- `decl_table.py`: 0 even when duplicate (module, name) pairs are written; 1 only for an undecodable or unreadable file or no `.lean` file; 2 usage error or SRC_ROOT not a directory.
- `rh_anchor.py --selftest`: 0 all cases pass; 1 any case fails; 2 usage error (it has no other command line); 3 no case ran. (It has no exit 4: it has no normal run to refuse.)
- `notes_meta.py`: 0 every note passed (listings do not count); 1 any finding of class ERROR; 2 usage error or an input that cannot be read (a note or strings file that is not UTF-8, an outline or strings file that is not JSON, a decls row that is not six columns, a `--base` that is not a commit), nothing on stdout; 3 CHECKED NOTHING (no note matches, the outline has no groups, or decls.tsv has no rows); 4 the self-test failed. `--selftest`: 0 all pass, 1 any fails, 2 usage, 3 no case ran.
- `note_cite.py`: 0 done (or a dry run printed); 2 usage error, an input that cannot be read (also a `--src` file that is not UTF-8), or a note that cannot be written; 4 the self-test failed, nothing done; 5 REFUSED (the one-line reason on stdout), nothing written; 6 a post-condition failed (a bug in the helper), nothing written. `--selftest`: 0 all pass, 1 any fails, 3 no case ran.
- `build_site.py`: 0 built; 1 refused, nothing written (an error of `notes_meta.py`, a strings key missing or a forbidden word, a build rule that failed, a non-empty OUT_DIR without `--force`, a release line found in an output); 2 usage error, an input that cannot be read or a site that cannot be written (one line, nothing on stdout, nothing left behind); 3 checked nothing (no note matches, or no `.lean` file under SRC_ROOT); 4 the self-test failed. `--selftest`: 0 all pass, 4 any fails, 2 an unknown id after `--only`.
- `in_closure.py`: 0 only if every site is INSIDE or OUTSIDE; 1 for an AMBIGUOUS or NOT A MODULE site, or no site; 2 usage or input error, or a control equal to the start; 3 a broken control.
- `import_closure.py`: 0 printed; 1 unresolved imports under the root's own folders (closure would be under-counted); 2 usage error or no file for the start module.
