# Text tools for reading the Lean source

These are text tools; they find where to read, they do not prove a dependency. Python 3, standard library
only. Each one runs its own self-test first and refuses (exit 4) if it fails. `--selftest` shows the cases. In `notes_meta.py` a case id registered twice stops the tool at load with a message naming the id and both descriptions; ids are compared as exact strings, so `rec1`, `REC1` and `REC1 ` are three ids.

A run that checks nothing (no `.lean` file under SRC_ROOT) writes nothing. If OUT_DIR already holds a file that run
would have written, an earlier result looks like this run's to the next tool; so `scan_graph.py`, `alias_edges.py`
and `decl_table.py` print one more line after `CHECKED NOTHING`, `OUT_DIR holds files from an earlier run: <names>;
this run wrote nothing`, and keep exit 1. They do not delete the files.

For whoever writes the next self-test: **the expected value in a case is a literal, never read back from the tool.**
A case that computes its expectation with the code under test, or with a helper the tool exports, passes whatever
the tool does. Write the number, the line or the list into the case, and run a wrong version of the tool (a copy)
to see the case go red.

**`tools/scan_graph.py SRC_ROOT OUT_DIR`** answers: which files exist, how big, what do they import?
It writes `files.tsv` (one row per file, with word counts) and `edges.tsv` (one row per internal import).
`python3 tools/scan_graph.py SRC_ROOT OUT_DIR`

**`tools/alias_edges.py SRC_ROOT OUT_DIR`** answers: which theorems are only a wrapper around another
theorem, where is the target declared, and where are the names written out in full? It never picks
between two declarations with the same full name; it lists both.
`python3 tools/alias_edges.py SRC_ROOT OUT_DIR`

**`tools/decl_table.py SRC_ROOT OUT_DIR`** answers: which named declarations are in each file, on which lines?
It writes `decls.tsv` (module, name, kind, first line, last line, basis) and `decls_dup.tsv` (every row whose
module and full name occur more than once; it never picks one). The lines are the text rule's extent, not Lean's;
the rule lives in `tools/lean_decls.py`, which `alias_edges.py` also uses. `example` lines and instances with no
name are not rows; they are counted on the second summary line.
`python3 tools/decl_table.py SRC_ROOT OUT_DIR`

**`tools/rh_anchor.py`** is a small library, not a command: the one place that knows the anchor format of the
notes. A note carries its metadata in one-line comments, `<!-- rh-note {...} -->` (the header) and
`<!-- rh-block {...} -->` (a block anchor, on its own line after the paragraph, table or lean block it anchors),
so the rendered page does not change. The checker and the helper that writes anchors both import it. It reads and
writes the lines (`parse_note`, `format_comment`, `strip_anchor_lines`), says which element an anchor follows and
where a new one goes (`target`, `target_at`, `insert_after_line`; a new anchor goes at `append_after`, after any anchors already there), checks the shape of a block or header
(`problems`, `header_problems`, `block_id_ok`), reads the run of elements a `sketch` block covers (`run_at`) and numbers new ids (`next_block_id`). It checks shape only: not the
outline, not the declaration table, not whether a table row exists. Markdown is approximated by three rules (fences,
tables, one comment per line), not CommonMark; the LIMIT paragraph in the file lists what is not recognised.
`python3 tools/rh_anchor.py --selftest`

**`tools/notes_meta.py NOTES_DIR OUTLINE DECLS_TSV`** answers: is the metadata of the notes well formed, and does every
name in it resolve to one row of `decls.tsv`? It reads the outline (every group, its parent, level, order,
premises, roots and claim), each note's header and anchors, and, with options, more: `--src SRC_ROOT` checks that
a block's `file` is in the note's file table and its `lines` are inside the file, `--strings PATH` lists blocks
whose text opens with another kind's frame, `--base REV` checks that the note at REV and the current note, both with
their anchor lines removed, are equal byte for byte after that rule, except that text the note only GAINED as dated additions is listed, not refused (see below; this needs the `git` program; `--repo DIR` names the repository when it is not the one around
NOTES_DIR), `--today YYYY-MM-DD` sets the day the additions are checked against (a test hook; default the UTC date of the clock), `--glob PATTERN` changes which files are notes (default `[0-9][0-9]-*.md`, so this folder's
`tools.md` is not one). The format of the comments is read only through `rh_anchor.py`. A finding is one line,
`CODE path:line message`; `EXTENT-WARNING`, `FRAME-NOTE`, `NEW-NOTE`, `ADDITION`, `CLAIM-LIBRARY-WORD`, `ROOT-ROLE-MISSING` (while it is not required) and `RECOGNITION-WORD` are listings and never fail the run. Each
note prints `note <id> header ok, blocks N (kind=count ...)`, and the run ends with the counts by kind, what the
in-file and byte checks did or did not do, and `N notes, M findings, K warnings`. It checks shape and resolution;
it does not judge whether a claim is right, and the LIMIT paragraph in the file lists the title rules and the
translation rules that need a reader. Every group needs at least one root; a group with a null claim and no root passed
in the first version and is now a ROOT-COUNT error. The title rules the script applies are heuristics, named in the LIMIT. A dotted token (`Foo.bar`) or a CamelCase word (`getValue`) in a claim `text` or a `conditions` entry outside single backticks is listed as `CLAIM-LIBRARY-WORD` (once per token and text; a prompt to write it in backticks or in plain words, not a proof; the rule is exact in the LIMIT). A claim may carry `basis` (`read` or `census`), optional for now; a summary line counts the non-null claims that are objects by basis (a claim that is not an object is its own BAD-VALUE and is counted in none). A group may also carry three optional keys. `root_role` (`result`, `named_statement` or `object`) belongs to a claim, and the checker compares it with the kind of the group's root in `decls.tsv`: `result` if and only if the kind is `theorem` or `lemma`; every other kind (`def`, `structure`, `abbrev`, `inductive`, any other) takes `named_statement` or `object`; a mismatch is `ROOT-ROLE`. A claim with no `root_role` is a `ROOT-ROLE-MISSING` listing for now (the real outline has no roles yet) and an error once the constant `REQUIRE_ROOT_ROLE` is set to True. `recognition` says where we read the statement stands: a `form` (`known`, `variant`, `not_recognised`, `open_in_literature`), `reader` and `date`, and per form a `result` in plain words, `citations` (each with `source`, `where`, `opened_by`, `opened_on`, and optionally `url`, `source_date`, `says_open`) and a `difference`. The form `not_recognised` may also carry one optional `note`, a string that is not blank, saying what the step is in the release's own terms and what we looked for; on any other form with a known form `note` is `RECOGNITION-FORBIDDEN`, and `result`, `citations` and `difference` stay forbidden on `not_recognised`. The number of sentences in a note is not checked. It is refused on a null claim; `open_in_literature` is only for a `result` or a `named_statement` (on an `object`, or with no `root_role`, it is `OPEN-ROLE`; `established` stays for a named statement only), needs a citation with `says_open` true and its `source_date` (a year `YYYY`, a month `YYYY-MM` or a day `YYYY-MM-DD`, each a real date, validated here, and the page builder will print it as written; year 0 is refused; `opened_on` stays a full `YYYY-MM-DD`); the words `novel` and `unprecedented` in `result`, `difference` or `note` are an error, and `new`, `original`, `first`, `assume`, `assumes`, `assumed` are listed as `RECOGNITION-WORD` (a prompt to the signer and the reviewer, not a proof; a word inside single backticks is checked too). A named statement may carry `established`: `not_traced`, or the theorem or lemma (`by`, which must resolve to one row of that kind) with its reader and date; that its conclusion is the named statement is the reader's claim. The run prints `recognition: K known, V variant, N not recognised, O open in literature, M not written, of G groups with a claim` after the `claim basis:` line, counted by the tool and asserted to add up (`SUM-RECOGNITION`). The check of these fields against the lines of the release is the builder's, not this tool's. The third key, `title`, is a plain string written by the author: a noun phrase that names the role of the step (the term a definition defines, or what a step with no claim is), never a sentence. It is not empty, has no blank at either end and no line break (anything else, an object or a list included, is `BAD-VALUE`), and its first character is not a lowercase letter (`BAD-VALUE`, `title must start with a capital letter or a character that is not a lowercase letter`: a digit, a quote, a bracket, a symbol or a letter with no case passes, a Greek or accented lowercase initial is refused, and the author writes the capital since no code changes author text; a title with a shape fault has that finding alone, and the build stops on the checker's errors); it carries no reader, date, conditions or recognition. The page shows it on a card with no claim and on a definition or structure card, so a title on a group with a claim that is not a definition card by the shared predicate below (the group's `root_role` when it has one, else the kinds of its roots in `decls.tsv`; a root with no row is not judged; a group with a claim has one root, so several roots are `ROOT-COUNT` as well) is `TITLE-WITH-CLAIM`: an error, because a title the page would ignore is author text no reader sees, and the author must choose. A bad title is `BAD-VALUE` alone. A group may also carry `short`, the one line the closed card of the graph view shows: author text written by hand, optional, a string of 1 to 50 characters (counted as characters, not bytes: 50 is accepted, 51 refused) with no blank at either end and no line break of any kind (the rule the title uses: LF, CR, CRLF, VT, FF, FS, GS, RS, NEL, LS and PS, every break Python's `str.splitlines` knows); anything else, an object or a list included, is `BAD-VALUE` naming the group and the key (`short must be a non-empty string of at most 50 characters with no line break`). A backtick pair and non-ASCII text are accepted, and no capital is asked for. A group without it is unchanged. Changes to `short` are not edition-checked yet: it is not one of the reader-facing text fields the edition check compares, so adding, changing or removing it never needs an edition and is never `OUTLINE-CHANGED` or `EDITION`. With `--base REV`, a group present at REV whose `short` differs (added where absent, changed, removed) is the listing `SHORT-CHANGED <id> <old> -> <new>` (values as short JSON, `none` when absent; at any edition; a warning, exit code unchanged); a group not at REV prints nothing, and an invalid `short` is still `BAD-VALUE`. The summary line `short changes: K` follows `first claims` (`did not run` with the same reason where the others do). A `sketch` block (a reader's short account of a proof, written after the idea) carries `reader`, `date`, `decls`, `basis` (`source` or `compiled`; `compiled` needs a `build` string and `source` refuses one), and optionally `unexpanded` (a list of strings: what is left, printed on the reader's surface), `unexpanded_detail` (F53: a list of non-empty strings, the per-file entries with tactic names and line numbers, printed inside Evidence only; the list may be empty, absent is the same as empty, and only a sketch reads the key) and `span` (an integer of 1 or more, default 1: how many elements, ending at the one the anchor follows, the sketch covers). Only a sketch may carry `span`, and a sketch carries no `item`. The run may hold paragraphs and lists; a table, a fence, a heading, a quote, an HTML line or another anchor inside it is refused, and so is a span larger than the elements between the anchor and the previous anchor, heading or the start of the note. A block belongs to the group named in its note's header and anchors a root of that group when its `decls` include the root; the counts run over all the notes of the group. The checker refuses a sketch whose root has no argument block (`SKETCH-NO-ARGUMENT`), a second sketch on one root (`SKETCH-DUPLICATE`, naming both block ids), a sketch on a root that is not a result (`SKETCH-ROLE`: the group's `root_role` when it has one, else the kind in `decls.tsv`, theorem or lemma; each root of a null-claim group by its own kind), a sketch whose `decls` hold no root of its group (`SKETCH-ROOT`), and a span the run cannot cover (`SKETCH-RUN`, with the reason from `rh_anchor.run_at`). An argument block anchored on a root whose kind is not theorem or lemma is listed as `ARGUMENT-NO-PROOF`: a prompt to the reader, since a definition can carry small proofs inside; it never changes the exit code. The note line and `blocks by kind:` count seven kinds. The line `sketches: S of P steps with a proof read` is not printed by this tool: what a step is belongs to the builder, which counts it. `note_cite.py` is unchanged: its `--kind` takes the kinds from `rh_anchor`, but it has no flag for `basis`, so a sketch cannot be valid through it and is refused as `BAD-BLOCK`. Two notes whose headers carry the same `id` (exact strings, first header of each note) are `NOTE-ID-DUPLICATE`. **Dated additions.** A note may gain text after publication without a byte difference when every base line is still there, unchanged and in order, and each run of new lines begins, after any blank lines, with a heading (one to six `#`, a space, text) whose text holds a real date `YYYY-MM-DD`. The base is matched into the current text from the left (a repeated line is taken at its first match) and, if that leaves an illegal run, from the right (taken at its last match); the note is accepted when either gives only legal runs, and the runs of the first that does (left first) are listed. Two alignments are tried, not every possible one. Every real date in the heading may not be later than the day of the run and may not be earlier than the date in `release` of the note header **as published** (the text at `--base`, so editing or deleting `release` since then does not lower the limit) when that is written `rh-YYYY-MM-DD`; a published release with no date, or an impossible one such as `rh-2026-02-30`, gives no earlier limit, and the limit is the release's date, not the note's own. A run may not touch published text: the line before its first non-blank line and the line after its last one must each be blank or the edge of the note (a blank line inside the run counts; anchor lines are not text), otherwise it is a byte difference naming the run and the side; a run above the first published non-blank line (above the title) is one too. Fence state is kept: a published line that is inside a fenced block in one text and not in the other (an inserted marker that wraps published text in a code block, or ends a published block early) makes the note a byte difference, and the message names the inserted run. Each such run is printed as `ADDITION path:LINE N lines, heading TEXT` (the line in the file as it is on disk, N the lines of the run), is counted among the warnings, and never changes the exit code; the byte-check line ends `additions A`. Everything else stays a byte difference: a removed or altered base line, a run with no dated heading first, a date outside the window (the message names the date and the window), an impossible date such as `2026-13-45`, and a run inside a fenced block of the published text. One run that fails makes the whole note a byte difference. Two limits: a line that repeats an earlier base line can leave the original unmatched as a second run on both alignments, which then fails unless it is itself a dated addition; and a note whose last line has no line ending cannot gain text after it. The boundary rule looks at blank lines only, so a run that brings its own blank line on each side and sits between two table rows, or inside a list item, is accepted and splits that table or list. A byte difference is reported at its line in the current file as it is on disk (and its index without anchors), so a reader opens the file at that line; where text is missing from the current file the number points past the end of the text: the line after the last non-anchor line, which is an anchor line when anchors trail it and otherwise one past the last line of the file (not a line that exists), or 1 when the file has no non-anchor line. The strip rule is `rh_anchor`'s: a last anchor line with
no line ending of its own also removes the line ending before it, so adding or removing such a hand-typed last line can read as a
one-line-ending difference; anchors written by the helper carry their own ending. An anchor-looking line counts as text only inside
a fence, and a malformed `rh-` line is kept as text, so fixing it since REV is a byte difference. A block anchored to a list must name its top-level
item (`item`, 1-based, counted across blank lines: a loose list is one list; nested items are not numbered), except a `sketch`, which covers whole elements, a list included as a whole: a sketch whose target is a list is not asked for `item`, and `item` on a sketch is a block problem (`BLOCK-PROBLEM`, with none of the other item findings beside it); shapes of list a renderer may show differently are refused through a table
that is empty until the renderer control is in, for the anchored list of any block and, for a sketch, for every list in its run (a list that is not the target is named with its first line; a sketch with a bad span or an illegal run gets that finding and no shape finding). Limit: the shape keys `last_nested` and `followed_by_paragraph` describe an anchor adjoining a list, and no anchor follows a list in the middle of a run, yet the table is applied to every list as written, so whoever fills the table decides whether those two keys apply to a list that is not the target. The run prints a count line for the outline (and for the strings file and the
byte check when they ran); a header's group may be `root` only at level 0.
`python3 tools/notes_meta.py NOTES_DIR outline.json decls.tsv [--src SRC_ROOT] [--strings strings.json] [--base REV] [--today YYYY-MM-DD]`

**Editions (F44).** A published text is rewritten in place only in a change that raises a group's `edition` from 1 to 2 and gives it an
`edition_date`; `notes_meta.py` with `--base REV` reads `outline.json` as it was at REV and compares each group's reader-facing text
(the fields in `EDITION_TEXT_FIELDS`: the claim text and conditions, the recognition's result, difference and note, each citation's
`where`, `source` and `source_date`, `established`, and the group's `title`, which is reader-facing text and is compared as text). Every field whose own text the page prints outside its Evidence section is in that list. The fields that only choose which sentence the page prints (`recognition.form`, `root_role`, `claim.basis`, a citation's `says_open`) and `premises` (what a step rests on) are not text: a change to one is a change of substance, not a rewrite for readers, so the check lists it, with or without a bump, as `SELECTOR-CHANGED <id> <path> <old> -> <new>` (exit code unchanged; the summary says `selector changes: K`) and never compares it as text. The compare is strict on purpose: text byte for byte (a space, a newline, NFC against NFD is a change), lists in order (a reorder or a duplicate is a change); an empty list and no value are equal. A change with the bump prints one `EDITION` line (none beside a bad `edition_date`) and does not fail the run; a change
with no bump, a bump with no change, a second rewrite, an edition 3, a lowered edition and edition 2 on a new group are errors; a group
that left the outline is a `GROUP-GONE` listing; an outline that cannot be read at REV (missing, not JSON, no groups list, or a groups list holding a non-object) is one `OUTLINE-BASE` listing and the rule does not run; `groups: []` at REV is legal and compares nothing.
A first claim is not an edition (an edition records a change to text that was published, and a card with no claim published none). A group whose
`claim` is null or absent at REV and an object now has gained a first claim: the text paths that were empty at REV and are set now (`claim.*`
and `recognition.*` alike), and the removal of its `title`, need no bump, and the change is one listing `FIRST-CLAIM <id>` (a listing, exit code
unchanged; the summary says `first claims: K`, directly after `selector changes`, and `did not run` where that line did not run). A new group
that carries a claim is listed the same way. A first claim with edition 2 (set now, or kept from REV) is the refusal `EDITION-FIRST-CLAIM`
(`a first claim is not a rewrite; remove edition and edition_date`); a title that is reworded beside the first claim, or any other text path that had a
value at REV and now differs, is still `OUTLINE-CHANGED` (published text was altered; make it a separate change); the selectors keep their
`SELECTOR-CHANGED` listings beside the `FIRST-CLAIM` line. A group at edition 2 at REV whose claim is null retires the mark in the same change: the first claim
that removes `edition` and `edition_date` is accepted (it is not `EDITION-DOWN`), and its line reads `FIRST-CLAIM <id>, edition mark retired with the title` when the title was set at REV and is removed, and `FIRST-CLAIM <id>, edition mark retired` when
the title stays (a group at edition 1 at REV has no such note); the
retirement is accepted whether or not the title is also removed, and an `edition_date` left behind is the ordinary `BAD-VALUE`. A first claim is listed and counted
(`first claims: K`) only when the check accepts it: a refused one (`EDITION-FIRST-CLAIM`, or `OUTLINE-CHANGED` for text beside it) prints its refusal alone and counts 0. An edition removed with no first
claim is still `EDITION-DOWN`, and a group at edition 2 whose claim stays null keeps every rule above.
`build_site.py` writes `edition` into each group file and into `data.js` (`null` at edition 1, else `{"number": 2, "date": "..."}`), counts
the groups at edition 2 in `manifest.json`, says it once on the first screen (the latest date, and a link to the tree of the first edition)
and once in each rewritten card's Evidence section (that card's date, and a link to `outline/outline.json` of the first edition). The
wording and the two addresses are the strings keys `edition_note_first_screen`, `edition_note_card` (the sentence of a group at edition 2),
`edition_note_card_note` (the sentence of a note, see below), `edition_link_label`, `edition_href_tree` and `edition_href_blob`; the addresses must be https and are not sentences. The static check lets an `<a class="edition-link">` with an
https `href` through, by class token, as it does a citation anchor. A page with no group at edition 2 is byte-equal to a page built before.

**Links to the notes (F60).** The website does not serve the notes' markdown files, so a relative note link (`notes/<file>`) answers 404 there. The
strings key `note_href` therefore takes a second, optional placeholder `{commit}` (the first is `{file}`, the note's file name, percent-encoded), and
`site/strings.json` holds `https://github.com/engram-agents/riemann-explained/blob/{commit}/docs/{file}`. `{commit}` is filled with the FULL notes
commit of the build (40 lower-case hex digits, the `commits.notes` that every JSON file carries), never with a branch name: a card's record of what
was read is a record at that commit, and a link that follows `main` could show text the cards have not been checked against. The address is the
`link` of every note in the group files, `level0.json`, `level1.json` and `data.js`, and the `href` of every note anchor on the page. A template that holds
`{commit}` when the build has no full notes commit (no `--notes-commit`, a tree with uncommitted changes, which stamps `dirty`, or any id that is not
40 lower-case hex) is refused: `BUILD-ERROR NOTE-HREF-COMMIT note_href holds {commit}, but the build has no full notes commit (it is <id>; give
--notes-commit and --repo, and build from a clean tree)`, exit 1, nothing written. A build from an unclean tree is refused because the stamped notes id is `dirty`, so to preview uncommitted notes, build with a copy of the strings file whose `note_href` is the relative `notes/{file}`. A template without `{commit}` builds exactly as before whatever the
commit is (both placeholders are optional). The static check lets an `<a class="note-link">` with an `https://` `href` through, by class token, as it does a
citation or an edition anchor; it is the one new exemption, and nothing else changed (`note-link` with `http://` or `//`, as part of another class word, on an
`img`, a form, a `<link>`, or on `src`, `action`, `formaction` or `xlink:href` is still refused, and so is an https note anchor with no `note-link`). The
builder writes the class on a note anchor if and only if its link starts `https://`, at the five places the page shows one (the notes about the whole in
the header, the argument's read-more link, the corrections list, a card's notes list and the block line of the Evidence section), through one helper,
`_note_open`; a relative template gives anchors with no class. The placing step is unchanged: the notes are not copied to the site.

**Editions of a note (F44B).** A note's header may carry `edition` (the integer 1 or 2; absent is 1) and `edition_date` (a real date
`YYYY-MM-DD`, not later than the day of the run; required at edition 2, refused at edition 1 or absent). `rh_anchor.header_problems` checks the
shape and `notes_meta.py` reports each bad value as a `BAD-VALUE` on the header line (edition 3 or more says `edition 3 needs a ruling`).
With `--base REV`, `notes_meta.py` compares the note without its anchor lines against the note at REV (a base with no header, or no
`edition`, is edition 1; so is a base whose header cannot be used for any reason other than an unusable `edition` value, which is the
`EDITION-BASE` listing below). A note is found at REV by its file name; a note renamed since REV is paired with its old name by its header `id` (see F52 below). A bump to edition 2 on a note whose text changed is one `EDITION` listing, `EDITION <note> +A -R lines, edition 1
to 2, <date>`, where A and R are the lines added and removed by `difflib.SequenceMatcher` over the lines (a replaced run counts on both
sides, a moved run counts on both); the note then has no `BYTE-DIFF` and no `ADDITION`. A bump with the text unchanged is `EDITION-EMPTY`
(an error). A note at edition 2 at REV follows the ordinary rules (a dated addition is legal, any other change is `BYTE-DIFF`); edition 1 or
none after edition 2 is `EDITION-DOWN`, a changed `edition_date` is `EDITION-DATE-CHANGED`, and edition 2 on a note that is not at REV is
`EDITION-NEW-NOTE` (errors). A base whose edition is not usable is an `EDITION-BASE` listing and the rule does not run for that note. For a
note at edition 2, `EDITION-BLOCK <note> <block id> element <n> <kind> -> <n> <kind>` lists each block (matched by id) whose target element
changed its place in the note (the n-th element, headings counted) or its kind, and `EDITION-BLOCK <note> <block id> gone` a block that is
no longer there; these are listings and say nothing about wording. The run prints `edition check: N groups compared to REV; K notes compared
to REV` and `editions: K of N notes and J of M groups at edition 2`. A bump whose `edition_date` is missing, not a real date or later than
the day of the run keeps its `BAD-VALUE` (an error) and the rule still prints its own line, `EDITION <note> +A -R lines, edition 1 to 2, no usable
date`, or `EDITION-EMPTY` when nothing changed, so the text change is not hidden behind the bad date.

**What no bump covers in a note (F52).** With `--base REV`, `notes_meta.py` also compares the parts of a note that are not its text.
A note's `list_title` is author text (the heading of its link on the page) and is compared like a group's title: a change with no bump is
`BYTE-DIFF <note> list_title changed from <old> to <new>` (an error; also at edition 2 at REV), and under a bump it counts as one removed and
one added line of the `EDITION` listing, so a bump whose only change is the title is not `EDITION-EMPTY`. A note's `group` and `level`
say where it is shown: a change against REV is the listing `PLACEMENT-CHANGED <note> <field> <old> -> <new>` (one per field, `group` first, at
any edition, exit code unchanged). An anchor that now points at a different element than at REV is the listing `RE-POINTED <note> <block id>
<old first words> -> <new first words>` (blocks matched by id; the element differs when its kind differs or its first 8 words differ, not when only
its ordinal moved, so a dated addition above it is not a re-pointing; when the first words are equal and only the kind differs, for example a table and a paragraph line that reads the same, the line ends with the two kinds, `(table -> paragraph)`; a note at edition 2 gets `EDITION-BLOCK` instead, not both). Re-pointing
an anchor is a repair, not an edition: a bump whose only change is where anchors point is still `EDITION-EMPTY`. A note at REV that is not in
the tree now is the listing `NOTE-GONE <note>`; if exactly one note is gone and exactly one new note has the same header `id`, it is
`NOTE-RENAMED <old> -> <new>` instead, and the new note is checked against the text of the old name (a rename with a rewrite and no bump is

The built page is also checked against one list of the elements it may hold, and the attributes of each (`ALLOWED_ELEMENTS` in `build_site.py`: 40 elements and 55 element-attribute pairs); no other element or attribute name may be on it. The check reads the start tags of the built `index.html` after it is rendered and before anything is written (not the CSS, not `data.js`), and looks at element names and attribute names only: attribute values and the text inside `<style>` are not checked here, and a `javascript:` or `data:` value of an `href` is a limit of the separate static check, which looks only for http(s) and protocol-relative addresses and the request APIs. The list is the 28 elements and 17 pairs the builder emits, measured over the five self-test fixture pages (EL4 pins them; an entry no path emits is not kept: `<time>` was removed when the dates left the page), and the MathML set, which the formula converter writes (a page with a formula holds it; the fixture pages do not). That set is 12 elements (`math mrow mi mn mo msub msup msubsup mover munder munderover mspace`), with `mathvariant`, `stretchy` and `form` on those only, `width` on `mspace` alone and `accent` on `mover` alone. The 17 pairs of the page are `class` on `a article details div dl h3 li p section span ul`, `href` on `a`, `id` on `article`, `lang` on `html` and `charset`, `content` and `name` on `meta`; which `meta` tags may stand is a separate rule, below (F55). An element or an attribute outside the list (a `<script>`, an `<annotation>`, an `<iframe>`, an `onclick` on a `<p>`, an `href` on a MathML element, a `style` where the builder has none) is refused as `PAGE-STATIC element <name>` or `PAGE-STATIC attribute <name> on <element>`, exit 1, nothing written, the same code as the other static findings; every bad attribute of a tag is listed, each against its own element's list (a `data-*` attribute is refused too). `style` and `title` are the allowed elements `html.parser` reads as text wherever they stand (the check takes this set from the parser's own lists, and a case pins it, so a future raw-text element must be classified); a browser reads their content as text only in HTML content, and as markup directly inside MathML, where the parser would not report a tag behind them. So each is allowed only in the opening run of the page, the start tags before the first one that is not `html`, `head`, `meta` or one of them (on the real page: `html`, `head`, `meta`, `title`, `style`), and refused after it, as `PAGE-STATIC element <name> outside head` (measured with html5lib 1.1: `<math><style><img src=x onerror=alert(1)></style></math>` builds an `<img onerror>` there, and the name check alone returned nothing). The rule reads start tags, because an end tag that a browser ignores (`</head>` while `<math>` is open, `</body>`) pops what `html.parser` tracks and not what a browser tracks: a rule built on end tags was passed by `<head><math></head><style>` and `<body><math></body><style>` (and the same with `title`), each a live `<img onerror>` in html5lib 1.1. No end tag reopens the run; the one end tag looked at is `</head>`, which only closes it, so it can add a refusal and never remove one. **What this does not claim:** the check is a name check on the tags as `html.parser` sees them, not a browser-grade parse, and a page it passes is not shown to parse to the same tree in a browser. Other differentials between `html.parser` and the HTML spec's parser are known to exist and are not measured here: the MathML text integration points and `annotation-xml`, attribute quoting, and how a misnested tag ends (the other raw-text elements are not allowed, so they are refused by name). Comments and CDATA are no longer on that list, because they are refused by construction: every comment (an ordinary one too, and `<!x>`, which the parser hands over as one) is `PAGE-STATIC comment`, every processing instruction is `processing instruction`, and every declaration but one `<!doctype html>` before the first start tag (compared lower-cased, so the page's `<!DOCTYPE html>` is the same doctype) and every unknown declaration such as `<![CDATA[` is `declaration`; markup `html.parser` still holds back at the end of the page (an unterminated comment, CDATA section, tag or style, which it never reports and a browser still reads) is `unterminated markup`. That is stricter than a browser needs: a comment is harmless to a browser, and the page has none (measured: no comment, no processing instruction and one declaration, `<!DOCTYPE html>`, on the real build and on every fixture page the self-test builds). Only the opening run may hold a raw-text element: a page that needs one elsewhere must change this rule, with its case. The search that found no page passed by the rule with a live `<img>` was bounded (html5lib standing in for a browser, a hand-picked pool of the allowed start tags and five end tags, one to three tokens before the payload; a second search put comment, CDATA, processing-instruction and doctype tokens in front of an `<img onerror>` after the real `<body>`) and is not part of this repository. A new element or attribute on the page is a change to this list in the same change, with its case.

**The head of the page (F55).** After `<meta charset="utf-8">` and before `<title>` the head holds exactly two more lines, byte for byte, each once: `<meta name="viewport" content="width=device-width, initial-scale=1">` and `<meta name="robots" content="noindex">`. The first is for phones: without it a phone lays the page out at 980 px and scales it down to about 40 percent. The second is the builder's own instruction not to index the site: the site is served byte for byte, so no server adds one, and the instruction has to be in the page. Every other byte of the page is as before (four fixture pages, with the two lines removed, have the digests they had; the digests `ED4` and `UD12` pin moved by exactly these two lines). The element check above keeps `charset`, `content` and `name` as the attribute names a `meta` may carry, and a separate rule says which whole tags may stand: the charset tag and these two, each a literal tag (attribute, value and order), not "any name and content". Any other `meta` is refused as `PAGE-STATIC meta not listed` (an `http-equiv`, a `charset` of another value, a bare `meta`, the right attributes in another order), `meta name not listed` (a name that is neither `viewport` nor `robots`, `Viewport` too), `meta viewport content differs` or `meta robots content differs`; one of the three tags twice is `meta repeated`. Cases `HD1` to `HD5`.

**The build checks the head itself (F55, round 1).** `head_meta_problems(page)` reads the rendered page text, and `run()` calls it beside the element check (it is not part of `element_problems`, whose cases feed pages with only a charset tag). A page whose head lacks the viewport tag or the robots tag is refused as `BUILD-ERROR HEAD-META viewport missing in index.html` or `robots missing`, and a copy of either anywhere but the head (in the body, with the head one gone or kept) as `viewport outside head` or `robots outside head`: exit 1, `OUT_DIR` not written, no traceback. So a builder that drops a tag no longer ships a page without it; before this check only the fixture cases noticed. The check looks for the two literal tags, fixed when the file loads, so a change of the builder's own constants does not change what it looks for. Cases `HM1` to `HM3`. In the browser helper, an unsolicited WebSocket pong is ignored (`HD7`), and a page that never reports `readyState` `complete` fails as `the page did not finish loading in N polls of 0.1 s` (`HD8`, which drives the helper with a small stand-in for the browser written with the standard library, so it needs no Chromium).

**What can and cannot see the viewport tag.** A plain narrow desktop window (`--window-size=390`) ignores the viewport tag: measured, `innerWidth` is 390 with and without it, so every read of the page in such a window could not see it. Measured (HeadlessChrome 156.0.8078.4, one fixture page): `innerWidth` 390 and `scrollWidth` 390 with the tag, and 980 and 980 with the tag removed from a copy, which is the control that shows the case sees the tag. The lines of a card with no proof (F41, F49) name no kind, so each is true of a definition and of a structure alike, and they are in the voice of the statement line above them: `proof_not_applicable_line` is `There is no proof to read: this step is not a theorem. **The title of a card (F47, F48).** A group may carry a `title` (see the checker above); the group file and `data.js` carry it as written, `null` when there is none, and the level files carry none. A *definition card* is decided by THE definition card predicate (`definition_card` in `notes_meta.py`, which `build_site.py` loads and calls, so the checker and the builder share it): a usable `root_role` decides (`named_statement` and `object` are definition cards, `result` is not; a null claim has no role); with no role, a card is a definition card when it has a root and NO root, of any number, is a theorem or lemma; one theorem or lemma root among several makes it a result card; an unknown or empty kind is not a result kind, so it is a definition card; no root is not a definition card. A card needs a title (`needs_title`) when it has no claim or is a definition card. Any other card is a *result card*. The heading of a card, in the same `<h3>` as before: (a) no claim, a title, a result card: the label `title_label` (`What this step is:`) in `<span class="title-label">`, then the title in `<span class="title-text">`, then directly under the heading `<p class="no-claim-label">` with the `no_claim_label`, then the premises line (if any) and the status lines as before; the root's Lean name is no longer in the heading and stays in Evidence. (b) no claim, a title, a definition card: the same, with `definition_label` (`Definition.`) in `<span class="definition-label">` instead, and no joining word. (c) a claim and a title, a definition card: the heading is `definition_label` and the title only; the statement is the first paragraph under the heading, `<p class="definition-statement">`: the title, `definition_join` (`is defined as:`) and the claim text as a claim is rendered (formulas converted inside it, logged under the card id), in normal weight; the conditions list follows that paragraph. A definition card with no claim prints no join anywhere. (d) a claim and no title, or no claim and no title: as before. A result card with a claim is shown by its claim whatever the data holds. The title goes through the span rule and the formula rule like every author-written line, and is escaped like every string. The title text is in normal weight, no colour, one CSS rule (`.title-text`): the heading is bold, so the weight is what sets the title apart from the label. A premise row and the shared-root note (the two places the page names another card, `title_of`) show the title of a card that has a shown title, else the claim, else the root name. The shared-root note (`shared_note`, placeholder `{groups}`) names each other card that shares the root, as an in-page link to its card, joined by `, ` in the order of the ids; the group file keeps the ids as data (`shared_with`). No card's id is printed as text: it is in the `id` attributes and the `#` links only. A card that needs a title (no claim, or a definition card) and has none is listed `TITLE-MISSING <card id>` on standard output, in the order of the page, and the line `titles: T of K cards that need one` follows the facts check; while the constant `TITLE_MISSING_REFUSES` is False this never changes the exit code, and set to True the same cards refuse the build (`BUILD-ERROR TITLE-MISSING <card id>`, exit 1). `TITLE_MISSING_REFUSES` is False until the outline carries every title.

**Formulas (F26B).** A formula `$...$` on one line, outside code spans and link targets, is shown as inline MathML in every place the page shows author text: a claim, a condition, a note's list title, the first sentence and the text of an argument or interpretation block, a sketch's paragraphs, items, sub-items, `unexpanded` entries and `unexpanded_detail` entries, the recognition's result, difference and note, and a citation's source and where. One function does it, called from the span rule, so no place is missed. The converter is our own, a pure function over a closed subset of TeX, 70 commands (`FORMULA_COMMANDS`, version `FORMULA_VERSION`, now `2`, named in the run line as `own-subset-2 (70 commands)`): 37 Greek letters (the 11 capitals are upright, `mathvariant="normal"`, as TeX sets them), `\le \ge \leq \geq \ne \neq \pm \cdot \infty \dots \mid \lceil \rceil`, `\sum \prod \int`, `\ast` (the star's synonym: the same `<mo>∗</mo>` as `*` in every position, so `\chi^{\ast}` and `\chi^{*}` give the same MathML), `\max \min \log \cos`, `\bar`, `\mathrm`, `\operatorname`, `\bigl \bigr \big`, `\mathbb` and `\mathcal` for a closed list of letters, and the four spacing commands. `\mathbb{X}` and `\mathcal{X}` (one letter, in a group or braceless like `\bar`) are the Unicode letter itself in a plain `<mi>` with no attribute, for exactly the letters the notes use: `\mathbb` C, F, Z (U+2102, U+1D53D, U+2124; F has no code point in the Letterlike block, so it is the one in the mathematical alphanumeric block) and `\mathcal` H (U+210B); any other letter, or more than one, leaves the formula unsupported. The output is MathML Core only: no script, no annotation, no outside asset. The page CSS gives a lone `<mi>` `text-transform: none; font-style: italic` (and `mathvariant="normal"` upright), because a browser's default math-italic mapping needs glyphs no common font has. A formula wider than its line scrolls inside itself instead of widening the page: `math { max-width: 100%; overflow-x: auto; overflow-y: clip; ... }` (the first three declarations of the rule; the rest of it is the continuation cue, the next paragraph; no new element, no attribute). The vertical axis is `clip` because with `auto` the engine draws a scroll control beside every short formula. Measured in a headless Chromium at a 390 px window on the real page: the page's `scrollWidth` was 428 before the rule, wider than the `clientWidth` (375 in a 2400 px high window, which has a scrollbar; 390 in a window as tall as the page), and after the rule it equals the `clientWidth` (375, and 390 in the tall window); with every Evidence section open it was 475 before and equals the `clientWidth` after. The window is 390 px wide throughout; 390 is not a page width the rule produces. At 1280 px the only change in a full-page screenshot is 235 pixels (the right overhang of an italic letter is clipped by the formula's own box). Only Chromium was measured. Formulas are taken out before the bold marks are read, so `$x**2 + y**2$` is a formula and `**$x$ holds**` is bold around one.

Before anyone is expected to run them routinely, the launch moves to a debugging pipe.

A step file has exactly `card`, `children`, `commit`, `format`, `id`, `path` (the ids of the ancestors, top first; `[]` for a top step), `rests_on`. A closed card, and each child, has exactly `child_count`, `id`, `kind`, `path`, `proof`, `state`, `title`, plus `role` when the step has one; a child also has `parent_rests_on`, true when the step rests on that child. `role` is a short word, not the list page's sentence: the value of the strings key `role_named_statement` ("Named statement") for the role `named_statement` (`GRAPH_ROLE_WORDS`); the full sentence (`named_statement_use_line`) stays in the card markup of the list page. The word is at most 24 characters (`GRAPH_ROLE_MAX`: 24 accepted, 25 refused) with no line break; a longer one, or one with a line break, refuses the build, `GRAPH-ROLE <id> is longer than 24 characters` or `GRAPH-ROLE <id> has a line break`, exit 1, nothing written (cases GA14, GA15). The key `role_named_statement` stays in `site/strings.json` and is not in `index.json` `strings`. The `role` key of a card is absent, never null and never empty, for a step with no `root_role` (the 8 steps with no claim) and for a role that has no row in `GRAPH_ROLE_WORDS` (`result`, `object`). On the real build 4 cards carry it (`input-green`, `input-hypsalt`, `literature-statements`, `zerofreeall`); `topg` and `linkn` have none. A link is `{from, from_path, to, to_path}` and means `from` rests on `to`, the direction of the outline's `premises`; both paths are the ancestors of the two steps, which is the ancestors of their parent plus the parent's id (`[]` for two top steps; `[a, b, c, d]` for two children of a step at depth 4). A step file's `commit` is the `commit` of `index.json`. A premise on a sibling is a link in the file of their parent (in `index.json`, with empty paths, for two top steps); a premise on the step's own child is `parent_rests_on` on that child and in no `rests_on`; a premise on any other step refuses the build. On the real build: 23 step files; the top is `rh-from-everycharacter`, `primitive-to-all`, `three-inputs`; the widest step (`zeros-enter`) has 6 children; the deepest step has 4 ancestors; 14 premise edges, 7 of them between siblings (2 in `index.json`, 5 in step files) and 7 on a step's own child, none across subtrees; `kind` theorem 15, def 6, structure 2; `state` read 16, census 1, none 6 (14, 1 and 8 before two steps of the outline were given a claim); `proof` read 5, not_read 10, none 8, counted over the 23 steps (the `facts` of `level0.json` count the 3 top steps only, all three read; the two counts have different populations and are not to be compared).

`kind` is the Lean kind of the step's root, for every step (a step with no claim too; with several roots the first decides): `theorem` or `lemma` gives `theorem` (the checker's `RESULT_KINDS`), `def` gives `def`, `structure` gives `structure`, and a root kind outside those, or no root, refuses the build (`GRAPH-SYMBOL <id> kind <value> (allowed: theorem, lemma, def, structure)`). `state` is `read` when the statement is read, `census` when it is not and the claim's basis is census, else `none`. `proof` is `read`, `not_read` or `none` from the group's `proof_read` (the key of the group summary that the level files carry): true is `read`, false is `not_read`, null (no root has a proof: a definition, a structure) is `none`, which the page words as "no proof to read". `symbols` is built from one table in `build_site.py` (`GRAPH_SYMBOLS`, the table of F38) and is exactly `{order, kinds, proofs, states}`: `order` has the three arrays of keys in the order to draw them (`kinds` theorem, def, structure; `proofs` read, not_read, none; `states` read, census, none), and each of `kinds`, `proofs` and `states` maps a key to exactly `class` (a css class token: `kind-*`, `proof-read`, `proof-not-read`, `proof-none`, `state-*`), `words` (a key of the `strings` object of `index.json`) and `text` (the same words, resolved, for a reader who does not look in `strings`). The `words` keys are `symbol_kind_theorem`, `symbol_kind_def`, `symbol_kind_structure`; `sheet_statement_read`, `sheet_statement_census`, `sheet_statement_not_read` for the three states; `sheet_proof_read`, `sheet_proof_not_read`, `sheet_proof_none` for the three proofs, so the legend and the sheet's status line share one name per symbol (the three kinds say what is drawn: "Square corners: a result the Lean code proves", "Rounded corners, one line: a named object or statement" and "Rounded corners and an inner line: a bundle of named fields"; the legend uses the sheet's short words, "Statement read", "Statement counted, not read", "Statement not read yet", "proof read", "proof not read yet", "no proof to read"). `strings` holds exactly those nine keys and the eleven run-time keys (see "The run-time strings" below) with their values from the strings file (a `{n}` is left as written). `role_named_statement` is never one of them: the builder resolves the role word into the card's `role` from the strings file at build time, and the page prints `role` from the card. A kind, a state or a proof that has no row refuses the build (`GRAPH-SYMBOL <id> kind|state|proof <value>`); a row that no step uses is still listed. There is no row for an unknown kind: a step whose state is not known is drawn by `state` `none`, never by `kind`. The strings checker refuses a key whose name holds `not_read` except `statement_not_read_line`, `proof_not_read_line`, `sheet_statement_not_read` and `sheet_proof_not_read`.

The `title` of a card is one line from one function (`_card_line`), in this order: the group's `short` (author text, 1 to 50 characters, no line break, which the checker holds to); else its `title`; else, only for a step that has no claim, the strings file's `no_claim_label`; else no line. The first sentence of the claim is not a fallback, and the Lean name never is. The backticks of a span are removed from the `short` and from the `title`. The line is checked as it is resolved, for every step, not only the `short`: a step that has a claim and neither a `short` nor a `title` has no line, a line of more than 50 characters (counted after the backticks go: 50 is accepted, 51 refused) and a line that holds a dollar sign (TeX source: the face is text, so the author writes plain words) each refuse the build, `GRAPH-SHORT <id> <reason> (<n> characters)`, exit 1, nothing written; the list page is not affected. So a `title` of 60 characters on a step with no `short` is refused, and the same `title` on a step with a `short` is not looked at, because the `short` is the line. The checker (`notes_meta.py`) accepts `short` and refuses one that is not a string, empty, over 50 characters or with a line break; the builder reports a `short` of that kind once (`GRAPH-SHORT <id> is longer than 50 characters`, and so on, without the count). The refusals, each its own code naming the id, exit 1 with nothing written: `GRAPH-ID` (not `^[a-z0-9][a-z0-9-]*$`, or `root`), `GRAPH-DUP`, `GRAPH-PARENT` (a parent that is not a step), `GRAPH-CYCLE`, `GRAPH-FANOUT <id> has N children (more than 40)` (41 refused, 40 accepted; the root's own children, the `top` steps, count too, and the root is named `root`), `GRAPH-SYMBOL`, `GRAPH-EDGE <from> <to> crosses subtrees | names no step | cycle in rests_on`, `GRAPH-COUNT` (`child_count` against the children listed, `steps` against the step files, every listed id against a file) and `GRAPH-SHORT`. **The graph assets (G2a).** `--graph-src DIR` (default `GRAPH_SRC`, which is `viewer/graph/` in this repository: the parent of the `tools/` folder that holds `build_site.py`, then `viewer/graph`) names the folder the page code is copied from. With no folder (it does not exist) or none of those files in it, `assets` is `{}`, nothing is written under `graph/` but the data files, and the run prints `graph assets: none (no viewer/graph directory)` (the same line when the folder exists and holds no asset: it says where the builder looked, not what it found); with assets it prints `graph assets: N files, B bytes`. **The sink gate (G2a).** After the assets are read and before anything is written, the assembled tree (the assets, and `shell.html` under its own name when the folder has one; no `.md`, no test file, and never the source folder itself) is written into a temporary directory laid out like OUT_DIR's `graph/` (removed afterwards), and `tools/graph_js_check.py` is run over it. `build_site.py` loads that file by its path next to itself (the way it loads `notes_meta.py`; no `sys.path` entry) and calls its `run`; it keeps no list of forbidden tokens of its own, so the scanner's table is the only one (case GA6 counts, in this file outside the self-test, the names of eleven of those tokens: 0 of each; the cases hold the literals). **A cue that a formula continues (F51).** A formula wider than its box scrolls inside it, and a phone draws no scrollbar until it is touched, so the page shows, with no interaction, that the formula goes on: a soft shadow on the cut side only (on the right edge while there is more to the right, on the left edge while there is more to the left, on neither for a formula that fits, and the one on the right is gone when the scroll reaches the end). It is CSS only, in the same `math` rule: no element, no attribute, no script. It is the known scroll-shadow technique: two shadows with `background-attachment: scroll` are fixed to the box's left and right edges, and two covers with `local` move with the content and sit at its two ends, so a cover hides a shadow wherever the content does not continue (a formula that fits has both covers over both shadows). The rule is the wording file's, written into the `CSS` constant by script and not retyped. **The page has no colour of its own for it:** every colour is `Canvas`, `CanvasText` or `transparent`, the reader's own system colours (the shadow is 35% of `CanvasText` over `Canvas`), so the cue follows the reader's scheme with no branch (F51COL reads the rule token by token and refuses a hex colour, `rgb(`, `hsl(`, a named colour or a backslash, since a CSS escape can spell a colour name). The page declares no `color-scheme` (F51TEXT), so it is light today. **Measured** in a headless Chromium (Chrome for Testing 156, headless shell) at 390 px on the real page with every `details` open (a copy): 337 formulas, 9 overflow and 328 fit (the wording file measured 10 and 327 in Chromium 148; the difference is not explained and the numbers are not forced). Against the same page built with the old one-line rule (the formula's own ink is in both), the cut-side strip of the last 0.75em is darker by a mean luminance of 31 to 44 (of 255) on 8 of the 9 at the start (right edge) and at the end (left edge), and the other edge by 0.5 to 0.7; a formula that fits is within -0.3 to 2.6 on both edges. **The ninth overflows by one pixel (scrollWidth 291, clientWidth 290) and shows nothing visible** (drop 1.2): the cover is solid for the first 30% of its 1.5em, so, from the rule's geometry, the shadow appears once the content hangs over by about half an em (only the one-pixel case was measured). That is the technique's own limit. On a copy that declares `color-scheme: dark` the cut-side strip is lighter by up to 40 and the page background is 18, the mirror of the light case; the binary accepted no flag that forces the dark preference (four were tried), so the preference itself was not exercised. **Not measured:** Firefox, Safari, and a forced high-contrast mode. **To run the browser case:** `RH_CHROME=/path/to/a/headless/chromium python3 tools/build_site.py --selftest --only F51BROWSER`. The case is SKIPPED, with the reason, when the variable is not set to a file; the self-test reads no other path of the host. A formula outside the subset (an unknown command, `\frac`, an environment, an unbalanced brace, a backtick or a dollar sign inside, a character the tables do not hold) stays as written, whole, and is listed as `FORMULA-UNSUPPORTED <where> <the first 40 characters of the formula, marks included>`; `$$...$$` is not converted and is listed the same way. Known limit: the link pass runs before the formulas, so text shaped like a link inside a formula (brackets, then parentheses, as `$a [b](c) d$` or `$[a](b)$`) is read as a link first: the formula is converted from what is left and a spurious `LINK-OUTSIDE` is listed. Choices of the converter, pinned by cases: a letter is `<mi>`; digits with one decimal point are one `<mn>`; `+ - = < > / ( ) [ ] , ; : ! | . *` are `<mo>` (the minus is U+2212, `*` is U+2217; a fence or a bar has `stretchy="false"`, a bracket also `form`, because in a flat row a stretchy fence grows to the tallest sibling of the row); `\sum \prod \int` take limits in line (`msub`, `msup`, `msubsup`) and `\infty` is `<mo>`, as F26B says; a script is ONE token or one brace group, so `x^10` is x to the 1 followed by 0; a prime is U+2032 inside the token of a one-token `<mi>` base (`L'` is `<mi>L′</mi>`, `\zeta'` is `<mi>ζ′</mi>`, `f''` is `<mi>f′′</mi>`; capital Greek letters and function names keep their normal variant), because a headless-Chromium look at 1x and 2.2x showed a separate flat `<mo>` sitting in the top stroke of a zeta (gone at 1x) and an `msup` floating it high and apart; a base that is not a one-token `<mi>` (a number, a fence, a group) keeps a flat `<mo stretchy="false">′</mo>`; a script after a primed base starts with a thin `<mspace width="0.15em">` so the prime and the script do not run together (`r'^{-k}`); a prime after a superscript, a second superscript and a prime with no base are unsupported; `\bar` takes one token or one brace group (`\bar\chi`, `\bar{\chi}`) and gives `<mover accent="true">` over a stretchy U+2015 (a full-width overline; the macron and U+203E render tiny or partial); the `|` signs of one group (the formula or a brace group; parentheses are flat in it) pair in order of appearance, the first `form="prefix"`, the second `form="postfix"`, both non-stretchy, an odd leftover stays a flat non-stretchy `<mo>`; `\mid` and `\big|` are not paired bars; `\mathrm{..}` and `\operatorname{..}` give one `<mi mathvariant="normal">` per word and take scripts; after `\operatorname{..}` and `\max \min \log \cos` (the function-like commands; `\mathrm` is text, not a function), and after their scripts, a thin `<mspace width="0.167em">` is added when the next token of the same group is an identifier, a number, a group, a Greek letter, `\infty`, `\sum \prod \int`, `\bar` or another function (TeX's rule), and not before a fence, an operator, a relation, a prime, a script or an explicit space, nor at the end of a group; `\bigl \bigr \big` give the delimiter alone (no size); `\,` `\;` `\ ` `\!` give an `<mspace>` of 0.167em, 0.278em, 0.222em and -0.167em (pandoc's widths; `width` is the one attribute the allow-list lets through on `mspace`), a plain space gives nothing; an empty group is an empty `<mrow>`; a literal non-ASCII letter is `<mi>`, a symbol or punctuation mark is `<mo>`, any other non-ASCII character makes the formula unsupported.

`python3 tools/build_site.py NOTES_DIR outline.json decls.tsv strings.json OUT_DIR [--source-check SRC_ROOT] [--release-archive-sha HEX] [--notes-commit REV --repo DIR] [--graph-src DIR] [--force]`

**`tools/build_grh_skeleton.py --grh DIR --pin COMMIT --strings strings.json --out OUT_DIR --ilean-dir DIR [--outline outline.json] [--strings-overlay overlay.json] [--strings-overlay-graph overlay.json] [--source-prefix PREFIX]`** answers: what is the
skeleton of the map for a Lean repository that keeps its own index? `DIR` holds `CONTENTS.md` and `src/`. The tool reads the `## New` section of
`CONTENTS.md` (`###` headings are sections, a line that is only `**title**` is a group, a line ``- `New/<path>` (<n>): <title>`` is a file) and the import
lines of the files under `src/New`, and writes `graph/index.json`, `graph/step/<id>.json` and `graph/uses.json` under `OUT_DIR`. It writes graph data only: no
page and no assets (`assets` is `{}`). It builds rows and hands them to `build_site.py`'s `_graph_files` and `_graph_bytes`; it has no writer of its own, so
every refusal of the graph data (`GRAPH-FANOUT`, `GRAPH-ID`, `GRAPH-DUP`, `GRAPH-EDGE`, `GRAPH-STRINGS`, `GRAPH-ORDER` and the others) is that function's.
`--pin` is written as the `commit` of every file. `--outline` (default `outline/outline.json` of this checkout) is the repository's own outline; `--strings-overlay` is described under Kind.
A normal run does not run the self-test; `--selftest [--only ID,ID]` does, and `--selftest --grh DIR` also runs case SK13 on a real source (without `--grh` it
is skipped and says so).

The rules are mechanical; nothing is typed by hand, and the kind and the face line are the skeleton's own rules, not reading:

- **Order** is the order of the lines of `CONTENTS.md`; nothing is sorted and nothing comes from the file system.
- **Steps** are part (top, one per `###` heading), group (one per bold line) and file (one per file line): 353 steps on the real source. A part whose one
  file has no folder (`New/Main`) has that file as its child, with no group between; the part's id is the slug of the heading. A section whose files have no
  group line gets one anonymous group (its id ends in `--`, its title is empty).
- **Ids** start with `lean-`, so they cannot meet the ids of the repository's outline (`SKEL-ID-CLASH` if one does). A section id is its folder name in kebab
  case; a group id is `<section id>--<slug of the group title>`; a file id is its path after `New/` in kebab case. An id longer than 64 characters is cut to its
  first 57, a trailing `-` removed, then `-` and the first 6 hex digits of the sha256 of the whole id.
- **Titles** are the `CONTENTS.md` text exactly (a file line's text after the colon, a group's bold text, a part's heading); a backtick span keeps its backticks. The 50-character bound of the graph contract is not applied here (it lives in
  `build_site.py`'s `_graph_line_errors`, which this tool does not call): most titles of the real source are longer.
- **Kind, state, proof**: kinds are `part`, `group` and `file`, read off the structure of `CONTENTS.md`; every step has state `none` and proof `none`. No
  declaration is read. The symbol table for this tool (`_graph_files(symbols=)`) has only those three kind rows; its order lists are kinds `[part, group, file]`,
  states `[]`, proofs `[]` (`orders=`; a row that occurs and is drawn but is missing from its list is `GRAPH-ORDER`; a state or proof occurs only on a card
  whose kind is not one of the three). `index.json` also carries `sibling_layout: column` (`layout=`; any other value is `GRAPH-LAYOUT`). Each kinds row also has `card_words`
  (a strings key for the word on the opened card; only a kinds row may have it), The group and file rows also have `count_words` (`{many, one}`, two strings keys for the foot under an opened box: `count_group_one` "{n} group", `count_group_many`, `count_file_one`, `count_file_many`; `{n}` is a declared placeholder of exactly those four keys; the part row has none), so `index.json` `strings` is 27 keys here (20 on the live map). A card whose children all have one kind carries `child_kind` (`_graph_files(child_kinds=)`; off by default): a part of groups has `group`, the last part (its one child is the file Main) has `file`, a group has `file`, a file has none; it is omitted when the children differ and when there are none, and the builder refuses a `child_kind` that is not the kind of every child, or is set on a card with no children (`GRAPH-CHILDKIND`). The words of the
  three kinds, their card words and the kinds heading come from an overlay file, `--strings-overlay` (default `site/strings-lean.json`): its keys replace or
  add to the strings file for this map only, and no file is edited. The seven words above are placeholders until the wording seat says otherwise. Eighteen more keys are the
  page's OPTIONAL words (`GRAPH_OPTIONAL_KEYS` in `build_site.py`: `key_kinds_note`, `note_label`, `note_source`, `note_label_typeset`, `note_typeset_line`, `note_exact_button`, `note_render_button`, `key_lines_heading`, `key_lines_text`, `spine_lines_text`, `key_scope_text`, and the Graph view's seven words `view_cards`, `view_graph`, `graph_nodes_text`, `spine_content_label`, `spine_lives_in`, `spine_show_file`, `graph_failed_notice`; the wording is final, and `note_source` holds
  the placeholders `{source}` and `{commit}`): `strings` is 27 keys without them (the Lean map writes notes, so it holds at least the pair: 29), 30 with the first three, 45 with all eighteen, and any other extra key is refused `GRAPH-STRINGS`. The words are optional one by one except `note_label` and `note_source`, which come as a pair, and a word that is present must be a non-empty string (the next two bullets). Two of them depend on the edge basis: `key_lines_heading` and `key_lines_text` (the page reads them only beside an edge basis, see the strings-values bullet); `spine_lines_text` does not (the page learns it with the Graph view). The live map's table, order lists, key set and output are unchanged: with no argument the
  key is absent and the lists are the whole tables.
- **The note-word pair**: `note_label` and `note_source` come together, in four shapes. `note_label` alone is refused, and so is `note_source` alone, whether or not the map has notes (`GRAPH-STRINGS <the missing word> missing: <the present word> is present and the two words come together`). Neither word, with a non-empty `notes`, is refused naming both (`GRAPH-STRINGS note_label missing: notes are present and need both note_label and note_source`, and the same line for `note_source`). Both words are accepted with or without notes, and neither word with no notes is accepted (the live map, which has no notes). A refusal writes nothing and exits 1. Shape 3 (neither word with notes) can only arise in `build_grh_skeleton.py`, because `build_site.py` never passes notes; shapes 1, 2 and 4 apply to both tools. The half-pair rule is in `_graph_strings_errors`, so it judges the strings handed to the builder and the written `index.json` alike; the notes rule is in `_graph_files`, next to the note checks, because it needs the notes. A word is present when its key is in the strings. `build_grh_skeleton.py` calls the same builder code, and the Lean map writes a note on every file step, so the merged strings (the strings file plus the overlays) must hold both words (`site/strings-lean.json` does).
- **Strings values**: every value of a key that reaches `index.json` `strings`, required or optional, must be a string and not empty: `GRAPH-STRINGS <key> is not a string` (None, a number, a list) and `GRAPH-STRINGS <key> is empty`, one line per key, sorted, after the missing and unread lines and before the pair lines, in `_graph_strings_errors`. A whitespace-only value is accepted: this is the page's own rule at load, which tests the empty string and never a trimmed value. An empty word beside the other word is a complete pair by key, so it gets the empty line and no pair line; both empty is two empty lines. The live strings files hold no such value in a key that reaches `index.json`. The edge-basis words follow the page too: with an `edge_basis` in the index, `key_lines_heading` and the key `edge_basis.words` names must both be present (`GRAPH-STRINGS <key> missing`, sorted) and are judged by the rule above; without one, `key_lines_heading` and `key_lines_text` are refused (`GRAPH-STRINGS <key> is not a key the page reads without an edge basis`). With one, only the heading and the key it names are read, so an edge-only key that the basis does not name is refused with its own text (`GRAPH-STRINGS <key> is not a key the page reads: the edge basis names <words>`: the fault is a basis that names another key, not a missing basis). Which maps hold what: the live map (`build_site.py` alone) has no `key_lines_` key and no edge basis; a Cards-only Lean build (no `--strings-overlay-graph`) holds both words and has an edge basis naming `key_lines_text`, and the page accepts it; a Lean build with the Graph overlay adds `spine_lines_text`. A skeleton build with the heading but no `key_lines_text` is refused (no edge basis), as is one with `key_lines_text` but no heading (the heading is missing). `spine_lines_text` is the exception and is not refused: the page learns it with the Graph view, so until then the page at this checkout refuses an index that holds it, which `PGV1` asserts as a known, named divergence (the case runs the page's own `validateIndex` with node and is skipped without node). No PR checks are configured on this repository: the two self-tests (`build_site.py --selftest` and `build_grh_skeleton.py --selftest`) are the whole gate.
- **Graph overlay**: `--strings-overlay-graph FILE` (no default) adds the words only the Graph view reads; they live in `site/strings-lean-graph.json` (the spine's sentence `spine_lines_text` and the Graph view's seven words: `view_cards`, `view_graph`, `graph_nodes_text`, `spine_content_label`, `spine_lives_in` (with the one placeholder `{title}`), `spine_show_file`, `graph_failed_notice`), not in the Cards overlay. Without the option the build is a Cards-only build: none of the file's keys is in `index.json` `strings`, and `spine.json` has no `edge_basis` (its words key is absent, and the omission is legal); with it every key is in `strings` and `spine.json` carries its `edge_basis`. So a Graph-view build passes `--strings-overlay-graph`, and a build that passes only `--strings-overlay` is Cards-only. The file is read by the same reader as the Cards overlay (a file that is missing, not JSON or not an object is exit 2) and its keys meet the same `{n}` placeholder rule at build time (`{n}` only in the four count words). The value rules (no value starting `[proposal]` or `[placeholder]`, the word `edge` in none) are not checked by the build: case OVL1 holds them on the checked-in files, for both overlays. A key in both overlay files, or in the Graph overlay and the strings file, is refused `SKEL-OVERLAY-CLASH <key>` and nothing is written. A key of either overlay that the builder does not copy into `index.json` `strings` (the page's keys and `GRAPH_OPTIONAL_KEYS`) is refused `SKEL-OVERLAY-KEY <overlay file name> <key> is not a key the page reads`, all such keys reported (sorted by file name, then key), nothing written, exit 1; it is no longer dropped without a word (case OVK1; every key of the two overlay files of this checkout is one the page reads).
- **Links** (`rests_on`) mean USES: file F rests on file G when a constant reference of F's compiled index (the `.ilean` file of its module, read as JSON data only;
  `--ilean-dir` is the `lib/lean` folder of the build, has no default, and nothing is run or written there) names a name of G and has at least one usage. G is another
  `New` file; references to the file's own module and to modules outside `New` are ignored. The weight of the link is the number of distinct names of G that F uses.
  What the weights count, and a measured fact: a weight counts names that the source text of F resolves to in G, as the compiled index records them. Measured by the SHAPE of the
  name on the real source (pin `72fead10`, the compiled index of the 306 `New` files): 12,688 pair-name uses over 2,135 file pairs and 4,284 distinct names, and only 2 of the
  12,688 uses (0.016%) are a name the compiler made (both `eq_1` lemmas, one use each, on two different file pairs); no pair's weight is made only of such names. So the
  weights count names the author's text reaches, not compiler output. The limit: the test reads the shape of a name only, so it cannot see generated names that look ordinary
  (structure projections and constructors, lemmas made by `@[ext]` or `@[simps]`, names the elaborator picked in the usual shape); a test by declaration kind would be needed
  for those. Uses that never appear as a reference at all are another matter and are not counted (the page says so). The measurement script is not in this repository.
  A link is drawn only between two files of one group. The data is NOT reduced: every in-group use is a link, and each link has `weight` and `in_reduction` (true when it
  belongs to the transitive reduction of that group's use relation); the exact key set of a link on this map is `from`, `from_path`, `in_reduction`, `to`, `to_path`,
  `weight` (`_graph_files(link_info=)`; the live map's links keep four keys). A use across groups is not drawn: it is listed in `graph/uses.json`. There is no link on a part or a
  group. The graph of uses must be acyclic: a cycle is `SKEL-USES-CYCLE <ids of the cycle>`. A `New` file with no `.ilean`, an `.ilean` whose module is not the file's, an
  `.ilean` with no `CONTENTS.md` line, one that is not JSON or has no `module` and `references`, one with a reference key of an unknown shape, and one that is a symlink, not a
  regular file or over 16 MiB are `SKEL-USES <path> <reason>`, all reported. The file is read through one descriptor opened without following a symlink and without blocking,
  checked with `fstat`, and read at most the limit plus one byte, and its real path must be under the real path of `--ilean-dir`; a folder of `ilean-dir/New` that is a symlink is `SKEL-ESCAPE ilean/<path> symlink` and is never walked.
  Every `.ilean` the tool loads (the New files, the files the index of declared names reads under `--ilean-dir`, and the file of each spine row) must have a `version` that is
  exactly the integer 5 (`ILEAN_VERSIONS`; all 803 files of the real compiled index carry it): a missing key, or any other value (4, 6, the string `"5"`, `true`, `null`, `5.0`), is
  `SKEL-ILEAN-VERSION <path under --ilean-dir> <the value as JSON text, or missing>`, all such files of a stage reported (sorted), nothing written, exit 1. The report is per stage: a bad New file stops the build at the uses stage, so a bad file of Lib is not reported until the New files are fixed. It is named before any other fault of the file. An `.ilean` is read as JSON with Python's parser, so a duplicate key is last-wins: of two `version` keys the last one counts.
- **Limits of the bounded reader** (the one reader of `CONTENTS.md`, `INDEX.md`, the README, the source files and the `.ilean` files). (a) A regular file inside the source folder that is a
  hard link to a file outside it passes the path check and the real-path check and is read; nothing in the tool can tell, so the source folder must be trusted for hard links.
  (b) The path is checked (`lstat`, containment) and then opened: `O_NOFOLLOW` closes the symlink case at the open, but only for the final path component: a directory component swapped for a symlink after the check is not caught.
  A regular file swapped in between the check and the open is read as what it is. Both are stated limits; no behaviour is added for them.
- **`graph/uses.json`** (format 2) is `{"commit", "format", "imports", "uses"}`. `imports` lists, for every file step, the ids of the `New` files it directly imports (from
  its `import` lines), sorted. `uses` lists, for every file step, `{"id", "names", "same_group"}` for every file it uses, in any group, sorted by id (`names` is the weight).
  Both keys are present for every file (a list may be empty). It is not part of `index.json`.
- **Notes**: the step file of every file step gains one key, `note`: `{"source", "text"}`. `text` is the inner text of the first `/-!` ... `-/` block of the
  source file, byte for byte: the delimiters are excluded, nothing is trimmed, no newline is changed (a CRLF stays a CRLF), and the nesting of `/-` and `-/` is
  counted (Lean comments nest). Only blank lines and `import` lines may come before the block. `source` is `--source-prefix` (default `grh/src/`) followed by the
  CONTENTS path and `.lean` (`New/A/B` gives `grh/src/New/A/B.lean`). Parts and groups carry no note, and `index.json` and `uses.json` are unchanged. The note is
  carried, not rendered: the data holds the text and the page escapes and typesets it. A file with no note, an unterminated block, text before the block, bytes that
  are not UTF-8, a file that is not a regular file (a symlink, a directory, a FIFO) or one over 1 MiB is `SKEL-NOTE <path> <reason>` (`no-note`, `unterminated`,
  `text-before-note`, `not-utf-8`, `symlink`, `not-a-regular-file`, `too-large`), all of them reported. The file is read through one descriptor that is opened without
  following a symlink and without blocking, checked with `fstat`, and read at most the limit plus one byte. `build_site.py`'s `_graph_files(notes=)` writes the key
  and refuses `GRAPH-NOTE <id> <reason>` (an unknown id, a step with children, keys other than `source` and `text`, a value that is not a string). A module note is
  prose, not a declaration, so the attribution lookup for the code the repository takes from Mathlib does not apply to it; it does apply to the next phase, the
  declarations, and no declaration sentence or snippet may be displayed before that lookup is wired. Nothing of the repository's text is published before the
  Sources and licences page ships in the same deploy.
- **The spine** (`graph/spine.json`, `{commit, format 1, links, nodes}`): one node per row of the table under `## The last step` of `INDEX.md` (read through the bounded,
  contained reader, at most 1 MiB; a table row with the wrong number of cells is `SKEL-INDEX <line>`). A node has `theorem` (the first cell) and `content` (the third), byte for byte
  (only the one space of padding of a cell is removed), `file` (the step id of the row's file), `id` (`spine-` and the slug of the first name, at most 64 characters, cut as the other ids),
  `names` (the backticked names of the first cell, as written), `constants` (each name resolved to EXACTLY ONE declaration of the row's `.ilean`: the name, `New.` and the name, or `New.`
  with a leading `D.` read as `Data.`; none or several is `SKEL-SPINE <row> <name> <reason>`, all reported) and `source` `grh/INDEX.md`. A spine id equal to a step id or a live
  outline id, or used by two rows, is `SKEL-ID-CLASH`. Links join rows: row A rests on row B when a constant of A reaches a constant of B by ANY chain of uses (through unnamed and
  Lib declarations) over the usage records of every `.ilean` under `--ilean-dir` (a usage names the declaration it is in; a usage with none and a use of a declaration inside itself
  give no edge; the walk is iterative). Every link is kept, `in_reduction` marks the transitive reduction, and two rows that reach each other are `SKEL-SPINE-CYCLE`. An edge is a name
  written in the source of one file and declared in another: a syntactic mention, so the edges are a lower bound (what Lean's automation or instances use without naming it is not recorded).
- **Direct mentions**: each node also has `mentions` (the declarations of New or Lib that the text of its declaration(s) names directly, not the row's own constants, not a constant
  outside New and Lib, not a structure field) and `counts` `{mentions, no_doc, other_constants}` (`other_constants` = the distinct constants named that the index does not list as a
  declaration: other libraries, structure fields, generated names; their kind is not guessed). A mention has `constant`, `kind`, `line`, `module`, `file_path`, `first_use` [line, column] (a 1-BASED line and a 0-BASED column, as the index counts columns; `line` and `doc.line` are 1-based too),
  `doc` {line, source, text} when the declaration has a doc comment, `file` for a New declaration (a Lib one has no step) and `spine` when it is itself a spine constant. The kind is the
  last of theorem, lemma, def, abbrev, structure, class, inductive, instance, axiom, opaque, example before the name on the name's line, as the author wrote it (`SKEL-KIND <constant>` when
  there is none or the source cannot be read through the bounded, contained reader); the doc comment is the text from `/--` on an earlier line through the `-/` that closes it, the nesting of `/-` and `-/` counted by the same counter the module note uses (an inner `/- ... -/` stays inside the doc; a doc that never closes is `SKEL-KIND <constant> unterminated doc comment`). `doc.text` INCLUDES its delimiters (`/--` and `-/`) while `note.text` EXCLUDES them: a view that strips them later is changing the repository's bytes and must say so (mark it as ours). The order is the
  reading order of the proof: the row's declaration in the table's name order, then the smallest use position, then the name.
- **The repository's sentences**: each row of `## Steps of the argument` whose file is a New step is carried on that step's file as `index_rows` `[{source, text}]` (the first cell,
  in table order); a row whose file is in Lib is carried on no step and listed in `graph/uses.json` `lib_index_rows` `[{file, source, text}]`; a row naming a New file that is not a step is
  `SKEL-INDEX`. A file step also has `spine_rows`, the spine ids whose row is in that file (absent when none). These are set through `_graph_files(step_extra=, index_extra=)` (optional;
  `GRAPH-EXTRA` for an unknown id, a key already used, a value that is not JSON).
- **Open-scale floor**: `--open-scale-floor N` (no default) gives `index.json` the optional top-level key `open_scale_floor`, written as the number is given (`1` stays `1`, `1.5` stays `1.5`). Anything but a positive finite number (zero, a negative, nan, inf, a number too large to be finite such as `1e400`, text that is not a number, a bool, an empty string) is `GRAPH-SCALE-FLOOR <value>` (exit 1, nothing written); a missing value is exit 2. Without the option the key is absent, as on the live map. The key goes through `_graph_files(index_extra=)`.
- **Note review**: every file step's `note` has the keys `review`, `source` and `text`; `review` is exactly `{"state": "converter"}` on all 306 notes (the page's rendering of the note is converter output, read by no one), and `_graph_files` refuses a note whose `review` is anything else (`GRAPH-NOTE <id> review must be exactly {"state": "converter"}`). The name `converter_version` is reserved for later states and is not used yet. A part or a group has no note.
- **Scope text** (`key_scope_text`): an optional page key of `index.json` `strings` (in `GRAPH_OPTIONAL_KEYS`). The overlay holds the wording seat's text with `{readme_quote}` where the repository's own words are quoted (the placeholder is declared for this key only); the builder fills it with line 15 of `grh/README.md` minus its closing colon, read through the bounded, contained reader, and the written value is checked, after the quote is filled in, for the placeholder names the format declares for another key (refused as below). That is the whole check: an undeclared `{foo}`, a lone brace, and `{readme_quote}` brought in by the quote itself are not looked for, so the written value is not shown to hold no placeholder at all. The value must hold `{readme_quote}` exactly once and the key is the only reason the README is read (a build without the key needs no README). Refusals, `SKEL-README <what> <reason>`: `README.md` missing, symlink, unreadable, too large, not UTF-8 or not a regular file (a directory, a FIFO); `has no line 15`; `line 15 does not end with a colon`; `key_scope_text has no {readme_quote}`; `has {readme_quote} twice`; `key_scope_text placeholder <name>` (the filled value carries `{<name>}`, a placeholder declared for another key, for example `{source}` or `{n}`; one line per name, sorted). The text passes strings rule R3 as it is (no exemption of its own; `proves` is not a forbidden word).
- **Maths-view note words**: `note_label_typeset`, `note_typeset_line`, `note_exact_button` and `note_render_button` (`Show in maths type`) are optional page keys of `index.json` `strings`, all four in the overlay of the Lean map and none with a placeholder; the builder takes each as an optional key and does not require all four together (the page shows the maths view only when it has all four).
- **Edge basis**: `index.json` has the optional top-level key `edge_basis`, the OBJECT `{basis: "names-written-in-source-from-compiled-index", words: "key_lines_text"}`: `basis` is a fixed value (an edge is a name written in the source of one file and declared in another, from the compiled index; a lower bound) and `words` names the key of `strings` that states it in words. The sentence itself is not in `index.json`; it lives once in `strings` (`key_lines_heading`, `key_lines_text`, `spine_lines_text`, written by the wording seat). The key is written whenever the strings carry `key_lines_text`. `graph/spine.json` has its OWN top-level `edge_basis`, `{basis: "reaches-through-any-chain-of-uses", words: "spine_lines_text"}` (a spine link means the upper result reaches the lower through any chain of uses of the declaration graph, then reduced), written whenever the strings carry `spine_lines_text`; its sentence is `spine_lines_text`, never `key_lines_text` (a spine whose words key is the index's, or whose basis is the index's, or that has other keys, is `SKEL-SPINE-BASIS <key>`). a map that carries `edge_basis` must carry the key `words` names (`GRAPH-STRINGS <key> missing`).
- **`graph/uses.json` format 3** also has `used_by` (the inverse of `uses`, with the same weights and flags, for every file), `lib_index_rows` and `titles` (`{step id: {kind, path, title}}` for EVERY step: 353 on the real source, 9 parts with `path` [], 38 groups and 306 files; each equals the card title and path of its step file).
- **Invariants of the page-facing files** (a page may refuse a file that breaks one): `commit` is equal in `index.json`, `spine.json` and `uses.json`; every link `from` and `to` is a node id;
  every node `file` is a file step id; a mention's `file` (when present) is a file step id and its `spine` (when present) is a node id; `counts.mentions` equals the length of `mentions` and
  `counts.no_doc` the number of mentions without `doc`; `used_by` is the exact inverse of `uses`; `titles` holds exactly the step ids; when `edge_basis` is present, `spine.json`'s `edge_basis.words` is a key of `strings` and is not the index's words key. A mention with no usage position is refused
  `SKEL-MENTION <row> <constant> no usage position`, never given a default. The real-source case INVR checks each of these on the real output.
- **Completeness**: every `.lean` file under `src/New` must be a file line and every file line must exist (`SKEL-UNLISTED <path>`, `SKEL-MISSING <path>`, all

  FIFO, a directory, a larger file, or bytes that are not UTF-8 are `SKEL-NOTE <path> <reason>`, see Notes); a line of the section that does not parse, or a file whose folder is not its section's, is `SKEL-LINE <n>`.

ids that were cut, and one line per group (files, use edges, reduction edges, files with at least one drawn link, files with none, the longest path of

**`tools/assemble_grh_site.py --data DIR --pin COMMIT --strings strings.json --shell shell.html --out OUT_DIR [--graph-src DIR]`** answers: what is the page of a map whose data
the skeleton builder wrote? `DIR` is the skeleton's `graph/` folder (`index.json`, `spine.json`, `uses.json`, `step/<id>.json` and nothing else). The tool writes ONE flat tree into
`OUT_DIR`, the way the page reads it (the page fetches `index.json` and `step/<id>.json` and loads its scripts relative to its own address): `index.html`, `index.json`, `spine.json`,
`uses.json`, `step/`, the engine and page files and `graph.css` (every asset of `build_site._graph_assets` over `--graph-src`, default `viewer/graph/`), and `manifest.json`. This tree is the map's files and their manifest, and it is NOT yet the tree the website keeps: the website's `place.mjs` refuses a kept map folder unless `credits/index.html` is kept and listed in the manifest and the map's `index.html` links `credits/`, and a run without a credits page writes neither. Until the `--page` change adds the Licence and credits page, the website refuses this tree, loudly and by name. It has no
second implementation of anything `build_site.py` or `build_grh_skeleton.py` already does: it imports `_graph_assets`, `_graph_sink_errors`, `_graph_asset_errors`, `_graph_page`,
`_graph_bytes`, `_manifest_bytes`, `_graph_static_problems`, `_publish` and the page checks (`static_problems`, `graph_element_problems`, `head_meta_problems`, the code-on-surface scan)
from the one, and the bounded, non-following reader `_read_in` from the other.
- **Inputs** are read bounded and contained (4 MiB each for the three data files, the strings file and the shell, 1 MiB a step file, at most 2,000 step files); a symlink, a FIFO, a
  directory where a file belongs, a file over its limit or bytes that are not UTF-8 is `ASM-DATA <path> <reason>`, as is a file DATA should not hold (`unexpected`) or lacks (`missing`).
  `--shell` is the page's own shell (it lives outside `viewer/graph/`, where a second `.html` is refused); the shell `_graph_assets` finds in `--graph-src` is not used.
- **The pin.** `--pin` is a lower-case 40-hex commit; `index.json`, `spine.json`, `uses.json` and every step file must carry it as `commit`, every step's `id` must be its file name and
  `index.json` `steps` the number of step files (`ASM-PIN <file> <found>`).
- **The page** is `_graph_page` over the shell with `cards` empty, the About block `<p>` + the escaped strings key `about_text`, and `data-page-feedback="off"` on `<section id="graph-about">`
  (the page has no card articles and no page-level comment thread). The shell may hold the `{{S:front_scope_line}}` and `{{S:readings_front}}` tokens besides the builder's own; the
  strings value of `readings_front` is a template with one `{n}`, filled with the length of the `readings` list of `index.json` (`ASM-READINGS`). The assembled page then passes the builder's
  element, static, head and code-on-surface checks (`ASM-PAGE`), and every ref of the written page resolves inside the tree: an absolute, `..` or missing ref is `ASM-PAGE <ref> absolute|escapes|missing`. The refs of the written page must be files of the tree, exactly as named (`./graph.css` is `missing`, a link to `list/` is `missing`), so the shell given to the tool must not be the repository's shared `viewer/graph/shell.html`, which links `list/` twice. Every JSON file about to be written passes the static check as `build_site.py` runs it (`ASM-STATIC`).
- **Data is carried, not changed.** `spine.json`, `uses.json`, every step file and every asset are written exactly as read; `index.json` is the builder's index with ONLY `assets` replaced by
  the sha256 of each asset, written by the builder's own serialiser.
- **`manifest.json`** is `{"commits": {"notes": PIN}, "counts": {"steps": N}, "files": {path: sha256}}`: the sha256 of every other written file, `index.html` included. There is no release id
  and no archive hash.
- **Nothing is written on a refusal.** Every check runs first; `OUT_DIR` must be absent or empty (`ASM-OUT`); the tree is written into a temporary sibling and renamed into place, so a
  failure leaves `OUT_DIR` as it was. Two runs give byte-identical trees.
